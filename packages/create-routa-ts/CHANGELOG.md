# create-routa-ts

## 0.6.0

### Minor Changes

- db5d2ac: Make an outcome's `schema` optional, so a response can intentionally have no body.
  
  - An outcome with a `schema` requires `data` typed from it. An outcome without one forbids `data`, builds with `response.name()`, and sends an empty body at any status. An optional outcome `description` becomes the OpenAPI response description. Without it, Routa uses the humanized outcome name, so `notFound` becomes "Not found" instead of "Generated by Routa". Bodyless outcomes have no OpenAPI `content`, replacing the generic `{ "type": "object" }` fallback.
  - TypeScript rejects a `schema` on `204`, `205`, and `304` outcomes and on every `HEAD` outcome, informational `1xx` statuses, `304` outside `GET` and `HEAD`, and response schemas whose input and output differ or that use `.transform()`, `.default()`, `.catch()`, `z.coerce.*`, or codecs. `routa check` reports `ROUTA_RESPONSE_INFORMATIONAL_STATUS`, `ROUTA_RESPONSE_BODYLESS_SCHEMA`, and `ROUTA_RESPONSE_NOT_MODIFIED_METHOD`. Registering a hand-built contract that breaks the status and method rules throws at startup. A mutating response schema in a hand-built contract is caught by `routa check`, or at request time when response validation is on and the schema changes the returned value.
  - A handler result with a `type` that is not a declared outcome name no longer type-checks, even when its data matches another outcome. Build the result with `response.name(...)` or return a literal `type`.
  - Response validation never sends the parsed value. `routa dev` and `responseValidation: "always"` parse `data` and compare the result with the handler value; any change fails as invalid handler output, including unknown keys the schema would strip and the whitespace `z.url()` trims. `routa start` skips both by default and sends the handler value. Known outcome, data presence, and JSON serialization checks run in every mode.
  - `isBodylessStatus` keeps its meaning: `true` for the statuses HTTP forbids a body for (`204`, `205`, `304`). It no longer decides whether an outcome has a body.
  - Scaffolding writes a schema-less outcome for responses without content and for `204`, `205`, `304`, and `HEAD`, instead of a `z.unknown()` schema. JSON content that declares no schema still scaffolds a `z.unknown()` body.
  
  Migration: remove `schema` from `204`, `205`, `304`, and `HEAD` outcomes and return `{ type }` without `data`. Replace response transforms with wire-ready handler values. If a handler returned a `type` from a variable, return a declared name instead.
- f8283c8: Compose outcomes that share a status, and give middleware rejects the full outcome contract.
  
  - Generated OpenAPI no longer keeps the last schema written for a status. An operation's outcomes are its route `responses` plus the `rejects` of every middleware in its chain, and outcomes that share a status compose into one response. Body outcomes compose when each has a required property with a single string, number, or boolean literal value (`z.literal(...)` or a one-value `z.enum([...])`, read through component references and intersections) and the values all differ as text: the schema becomes a `oneOf` ordered by outcome name with that property as `discriminator.propertyName` (the alphabetically first one when several qualify), plus a `mapping` to referenced components whose names differ from their values. Headers declared by several of them project once, `required` only when every outcome requires them; cookies are listed once in `Set-Cookie`, which is `required` when every outcome requires some cookie, even different ones. The description lists each outcome's description in outcome-name order as a Markdown list. Nothing depends on source order, and Routa never falls back to `anyOf`.
  - `routa check` reports `ROUTA_RESPONSE_STATUS_AMBIGUOUS` for same-status body outcomes without such a discriminator, a body and a bodyless outcome under one status, and several bodyless outcomes under one status; `ROUTA_RESPONSE_HEADER_INCOMPATIBLE` for one header name with different schemas under one status (compared by content, so a component reference and an equal inline schema agree); `ROUTA_RESPONSE_COOKIE_CONFLICT` for one cookie identity from different `createCookie` declarations under one status; and `ROUTA_OUTCOME_NAME_COLLISION` for a route outcome and a reject, or two rejects, that share a name.
  - Middleware `rejects` now go through the same `routa check` and OpenAPI reader as route outcomes. Reject `headers` and `cookies` are checked and documented, a reject that `routa check` cannot read (a spread, a computed name, status, or description, an unreadable schema, or a `createMiddleware` config spread that could hide its `rejects`) reports `ROUTA_SCHEMA_UNSUPPORTED` instead of disappearing, a lifecycle-owned reject header reports `ROUTA_RESPONSE_HEADER_LIFECYCLE`, and a reject with a `schema` reachable from a `HEAD` route reports `ROUTA_RESPONSE_BODYLESS_SCHEMA` and fails registration.
  - A handler can return only its route's outcomes and a middleware only its own rejects; anything else is invalid handler output. Runtime cookie conflict messages name the producer, such as `middleware[0] reject "expired"`, and `routa check` messages name the middleware behind a reject.
  - `next()` now resolves to an opaque `MiddlewareContinuation`, the outcome the rest of the chain selected. A continuing middleware must return it unchanged: TypeScript rejects a copy or added headers and cookies with `Return the value next() resolved to, unchanged.`, and returning anything else after `next()`, including one of the middleware's own rejects, fails as invalid handler output. Routa validates and serializes the selected outcome before `next()` resolves, so later changes to the objects it was built from do not reach the response.
  - TypeScript flags a route outcome named like a reject of the route's own `middleware`, and registration fails for any route outcome and reject, or two rejects, that share a name. The registration message changed from `Duplicate middleware reject key "…"` to `Outcome "…" on … is declared by … and by …`.
  - `MiddlewareNext` and `MiddlewareRunArgs` lost their unused `TRejects` type parameter.
  
  Computed property keys in outcome declarations now fail with `ROUTA_SCHEMA_UNSUPPORTED` instead of silently omitting contract fields from generated metadata. Use static property names for route outcomes and middleware rejects.
  
  Migration: give same-status outcomes a literal discriminator (for example `kind: z.literal("created")`) or distinct statuses. Remove route outcomes that redeclare a middleware reject, such as a route `unauthorized` outcome next to an auth middleware's `unauthorized` reject; the reject is already part of the operation. A middleware that read or changed the result of `await next()` must return that result unchanged; move response decisions into the handler or a reject that returns before `next()`. Drop the `TRejects` argument from explicit `MiddlewareNext<…>` and `MiddlewareRunArgs<…>` references.
- 364608f: Let a named outcome set and clear cookies through typed handles.
  
  - `createCookie` is a new `@routa-ts/core` export. It declares a cookie once with a `name`, a value `schema` (a string, number, or boolean that does not change values), and static attributes: `httpOnly`, `secure`, `sameSite`, and `path` are required; `domain`, `maxAge`, `expires` (an ISO 8601 date-time string), and `partitioned` are optional. The handle's `set(value)` and `clear()` are pure and return typed effects.
  - An outcome lists the handles it may emit in `cookies`. The result's `cookies` is an array of effects for those handles only: it is optional, it is forbidden when the outcome declares none, and an effect for another handle fails TypeScript. A bare handle is optional; write `{ handle: session, required: true }` to require a `set` or `clear` effect for it, which TypeScript checks and Routa enforces in every validation mode. An outcome with a required cookie has no builder. Builders do not take cookies, so return `{ type, data, cookies: [session.set(token)] }`.
  - Routa validates, percent-encodes, and sends each effect as its own `Set-Cookie` field, never joined with commas, through the same finalization step as headers. Terminal middleware `rejects` accept `cookies` and share that path. `clear()` keeps the name, domain, path, and security attributes and adds `Max-Age=0` and an epoch `Expires`.
  - `SameSite=None` and `Partitioned` require `secure: true`; a `__Secure-` name requires `secure: true`; a `__Host-` name requires `secure: true`, `path: "/"`, and no `domain`. A path starts with `/`, uses printable ASCII without `;`, and has no trailing space; write non-ASCII paths percent-encoded. TypeScript catches these where the literal types allow it, and `createCookie` and `routa check` always do.
  - Cookie identity is name, domain, and path. One producer owns an identity in a response, so the same handle twice, or two handles with one identity, fails. The same name with a different domain or path is allowed and warns in `routa check` and at startup. A raw `Set-Cookie` header stays reserved.
  - Cookie value parsing and the comparison with your value follow `responseValidation` like the body and headers. Declared handles, required effects, one effect per identity, and safe encoding are checked in every mode.
  - `routa check` reads each `createCookie` declaration through relative imports, `export { name }`, aliases, and `export *` re-exports, and reports `ROUTA_RESPONSE_COOKIE_UNRESOLVED`, `_STATIC`, `_ATTRIBUTE`, `_NAME`, `_RULE`, `_VALUE`, `_CONFLICT`, and the `_SCOPE` warning. It accepts a `cookies` field in returned results.
  - Generated OpenAPI documents an outcome's cookies through one standard `Set-Cookie` Header Object that lists names and static attributes and says each cookie is a separate repeated field. The header is required, and its description names the cookies, when the outcome declares a required cookie. `openapi check` compares that description, so a changed cookie attribute is drift. It never includes values or examples, and adds no vendor extension.
  - Relative imports that name a directory now resolve to its `index.ts` instead of failing.
  - A `middleware.ts` file can export middleware declared later with `export { name }`, under an alias, or through `export *`. Generated route metadata now records each middleware by the `middleware.ts` file and the name it exports, so aliased middleware loads at startup. Explicit middleware exports take precedence over wildcard exports with the same name, and overlapping wildcard paths include an exported name once.
  
  Migration: none for existing outcomes. To send a cookie, declare it with `createCookie`, list it in the outcome's `cookies`, and return its effect from the handler instead of writing a `Set-Cookie` header.
- 4a1c2ed: Project Zod schemas to OpenAPI from source and check them in `routa check`.
  
  - `.describe()` and literal `.meta()` keys (`title`, `description`, `deprecated`, `example`, `examples`, `readOnly`, `writeOnly`, `externalDocs`, and `x-` extensions) now appear on the generated Schema Object at root, nested, inline, and component locations.
  - `components.schemas` now comes from source instead of the baseline. `.meta({ id })` names a component, an exported schema a route uses is a component named after its export, and an alias reuses its target's component. Two declarations that claim the same explicit `id` fail with `ROUTA_SCHEMA_COMPONENT_COLLISION`, even when their content is equal. Declarations named by the same export share one component when their projections are equal and fail when they differ.
  - `z.discriminatedUnion` generates `oneOf` with `discriminator.propertyName`, and `z.intersection` and `.and()` generate `allOf`, folding plain object members into one object unless a member, such as a record, constrains additional properties. As in Zod, the result rejects unknown keys only when every member is strict, and intersected parameter containers split into parameters even when their members are exported or described. `z.record()` key schemas generate `propertyNames`, and enum keys are required. Scaffolding maps `anyOf` to `z.union` and a discriminated `oneOf` to `z.discriminatedUnion`, so re-scaffolding an `anyOf` that has a `discriminator` now writes `z.union`.
  - Input schemas document the incoming side: `.default()` and `.catch()` make a property optional, and `.transform()` or `.pipe()` after a readable schema documents that schema. `z.stringbool()` is a `boolean` parameter and a `string` JSON body property. `z.preprocess()` and a leading `z.transform()` print a `ROUTA_SCHEMA_OPAQUE_INPUT` warning.
  - `routa check` now fails on schemas it cannot read (`ROUTA_SCHEMA_UNSUPPORTED`, `ROUTA_SCHEMA_UNRESOLVED`), metadata misuse (`ROUTA_SCHEMA_META_*`, `ROUTA_SCHEMA_REGISTRY`), and response schemas that change values (`ROUTA_RESPONSE_SCHEMA_MUTATION`), including record keys, `.check()` arguments declared in the same file, and `z.url({ normalize: true })`. `z.date()`, which has no JSON form, route `input` built from spreads or shared variables, response outcomes built from spreads, and `.check()` arguments or URL options Routa cannot classify now report `ROUTA_SCHEMA_UNSUPPORTED`. These replace the `ROUTA_OPENAPI_UNSUPPORTED_ZOD` warning, and generation no longer emits empty schemas for them.
  - Route inputs, outcomes, headers, and middleware rejects can use a schema imported by name from a relative module, through aliases and `export { ... } from` or `export * from` re-exports. Routa reads the declaration in its own file and names its component after the declared export. Package imports and tsconfig path aliases report `ROUTA_SCHEMA_UNRESOLVED`.
  - Middleware reject schemas resolve identifiers from the file that declares the middleware, following barrels and aliased re-exports such as `export { guard as adminGuard } from "./guard.js"`. Middleware imported through an aliased re-export no longer reports `ROUTA_MIDDLEWARE_UNRESOLVED`.
  - `routa openapi check` compares schemas by content, so inline and `$ref` spellings of the same schema are not drift.
  - New projects declare `zod@^4.6.7`, matching the `@routa-ts/core` peer.
  
  Migration: run `routa check` and fix each reported schema. Replace response transforms, defaults, and coercions with wire-ready handler values, and `z.date()` with `z.iso.datetime()`. If a route imports a schema from a package or through a tsconfig path alias (`ROUTA_SCHEMA_UNRESOLVED`), declare it in a project module and import it through a relative path. Then run `routa openapi check`; if it reports drift from corrected projections, such as query helpers now documented as strings or baseline-only component details, review the change and accept it with `routa openapi breaking --update-baseline`.
- 0a4e02f: Let a named outcome declare its response headers.
  
  - An outcome's `headers` is a Zod object keyed by lowercase header names with string, number, or boolean values (or literals and enums of them). The handler result's `headers` is required when any declared header is required, optional when all are, and forbidden when the outcome declares none. `response.name(data, headers)` and, for a bodyless outcome, `response.name(headers)` build the result. Outcomes without `headers` keep their current source.
  - Routa serializes each value to one header string, and bodyless outcomes can send their declared headers without receiving content headers. Declared names, required headers, and safe values (no line breaks, no surrounding whitespace, finite numbers) are checked in every mode. Zod parsing and the comparison with your value follow `responseValidation` like the body, so a header schema must not change values either.
  - A header has one owner. Routa owns `content-type`, `content-length`, `transfer-encoding`, `connection`, and `set-cookie`, and with `lifecycleHeaders` on it owns `deprecation`, `sunset`, and the successor `link`. A declaration that claims one, declares a name that is not lowercase, declares two names that differ only in case, or declares a value that is not a string, number, or boolean fails. TypeScript catches the rules it can know from the declaration alone: reserved names, names that are not lowercase, and values that are not scalars. `routa check` (`ROUTA_RESPONSE_HEADER_NAME`, `_COLLISION`, `_RESERVED`, `_LIFECYCLE`, `_VALUE`) and app registration also catch conflicts with lifecycle headers, which depend on the application's `lifecycleHeaders` setting and the route's `deprecation`, so TypeScript cannot see them. `routa check` treats any `lifecycleHeaders` value other than an omitted key or a literal `false` as possibly on, and a `createRouta` config it cannot read (a variable, a call, a spread, or a computed key) the same way. A default config with no local `createRouta` call, including a re-export, also counts as possibly on. A result that writes an undeclared header, the same header in two cases, or a header a lifecycle header also writes fails as invalid handler output instead of merging or overwriting.
  - Declared headers become Header Objects in the generated OpenAPI response, with the header's schema, `required`, and description. All response headers, declared and lifecycle, now leave through one finalization step.
  - `routa check` accepts a `headers` field in returned results next to `type` and `data`.
  
  Migration: none for existing outcomes. If an outcome already declared nothing, nothing changes. To send a header such as `etag` or `retry-after`, declare it in the outcome's `headers` and return it from the handler instead of setting it elsewhere.
