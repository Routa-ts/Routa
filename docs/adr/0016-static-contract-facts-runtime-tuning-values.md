# Static contract facts, runtime tuning values

Routa splits application configuration into two kinds of values. Contract facts change the HTTP contract: which operations exist, which framework failures an operation can return, authentication schemes, error mappings and deprecation. They stay statically readable, so generation never executes application code and committed `.routa/` state stays deterministic. Tuning values only adjust enforcement of an existing contract: timeouts, limits, concurrency caps, cache durations, CORS origin and header lists, header values and proxy trust lists. They are ordinary runtime configuration that may use any expression, including environment variables, and the runtime validates them once at startup. Generated state keeps no copy of them, so no runtime-versus-generated agreement check is needed.

Static analysis reads only whether a tuning-backed feature is enabled. A literal `false` disables it, an omitted key selects the documented default, and any other value counts as possibly enabled, so OpenAPI conservatively documents the framework failure it can produce. Guardrails that inspect tuning values run at startup rather than in `routa check`.

We chose this over keeping every value literal, which forced a rebuild to change a limit and duplicated an extractor and an agreement check for values nothing downstream reads. We also rejected evaluating `routa.ts` during generation, because import side effects and environment reads would make generated state differ between machines.
