Generate a request identity for every request, add opt-in correlation, and replace the automatic request events with safe ones.

- Every request that reaches a Routa app gets a UUID that Routa generates and never takes from the request. Middleware, services factories, and handlers read it as readonly `ctx.requestId`, every response carries it as `x-request-id`, and it holds for unmatched requests, validation failures, middleware rejects, authentication failures, `406`, automatic `OPTIONS`, `405`, and server errors. A response that a handler on the returned Hono app returns and the runtime cannot copy, such as a `101` upgrade response, goes back unchanged without identity headers, and `http.response.prepared` still records its status. It stays with `logger: false`.
- New `correlation` option in `createRouta` and `createHonoApp`: `true` reads `x-correlation-id`, `{ header: "x-trace-ref" }` another header, compared case-insensitively. Routa accepts one value of 1 to 128 ASCII letters, digits, `.`, `_`, or `-`, exposes it as `ctx.correlationId`, binds it to the request logger, and echoes it in the same response header. An absent, empty, repeated, or otherwise invalid value is ignored without rejecting the request. A header that is not a valid name, or that names `x-request-id`, a credential header (`authorization`, `proxy-authorization`, `cookie`, `set-cookie`), or a header Routa writes itself (`content-type`, `content-length`, `transfer-encoding`, `connection`, `allow`, `access-control-allow-methods`, `vary`, `deprecation`, `sunset`, `link`, `www-authenticate`), is rejected at startup and by `routa check`. New types `RequestIdentityContext` and `CorrelationConfig`.
- `ctx.logger` is now a request logger: a child of the configured logger bound to `requestId`, and `correlationId` when accepted, which event data and later `child()` bindings cannot replace. Without an accepted correlation ID its events carry no `correlationId`, even when the configured logger's bindings or the event data name one. The configured logger, and every module that imports it, stays without request identity. Services factories receive the same request logger.
- `http.request` is replaced by `http.response.prepared`, written once per prepared response with `requestId`, `correlationId` when present, `method` (a standard method or `_OTHER`), `route` (the route pattern or `[Unmatched]`), `status`, and `durationMs`. It says the response was prepared, not sent. `http.error` now carries `requestId`, `method`, `route`, `status`, and for invalid handler output `issueCount` and the distinct, sorted `issueCodes`, and no longer the request path, issue paths, or any error's message, name, stack, or authentication scheme. `services.cleanup_failed` now carries `failureCount` instead of a `failures` list of error messages, names, and stacks, and the request identity when a request's cleanup failed.
- `requestId`, `correlationId`, and `logger` are reserved context keys like `services`: TypeScript, `routa check` (`ROUTA_CONTEXT_RESERVED`), and registration reject middleware that provides one or passes one to `next()`, and an assignment that bypasses the types fails the request. `x-request-id` and the configured correlation header are reserved response headers: TypeScript (for `x-request-id`), `routa check` (`ROUTA_RESPONSE_HEADER_RESERVED`), and registration reject an outcome or reject that declares one, and Routa sets `x-request-id` last on every response and echoes an accepted correlation ID over any other value.
- `routa check` reads `correlation` from `src/routa.ts` without running it and reports `ROUTA_CORRELATION_CONFIG_UNRESOLVED`, `ROUTA_CORRELATION_HEADER_INVALID`, and `ROUTA_CORRELATION_HEADER_CONFLICT`. `ROUTA_CORRELATION_CONFIG_UNRESOLVED` also covers a spread, config argument, computed key, or default export Routa cannot follow whose type may hold `correlation`, read with the type checker; a part whose type has no `correlation` member, such as `{ host: string; port: number }`, is ignored, and so is the optional `correlation` that Routa's own `RoutaConfig` adds to every `createRouta` result. A default that `src/routa.ts` imports or re-exports from another module, such as `export { default } from "./config.js"`, is followed through the type checker to the `createRouta` call there, so `correlation`, `services`, and `authentication` written in it are read like local ones. `.routa/routes.gen.ts` exports `routaCorrelationHeader` when correlation is on, and startup refuses a `src/routa.ts` that disagrees with it.
- Generated OpenAPI documents `x-request-id` on every operation response, and the correlation header as optional when correlation is on. `routa scaffold` and `create-routa-ts` write `x-request-id` into the baselines they create.

Migration:

- Remove middleware that provided `requestId`, `correlationId`, or `logger`, and read `ctx.requestId` instead. To keep a caller-supplied ID, turn on `correlation` and read `ctx.correlationId`; it never replaces the request identity.
- Remove `x-request-id`, and the correlation header if you turn correlation on, from outcome and reject `headers`.
- Update log queries and alerts from `http.request` to `http.response.prepared`, and from `path` to `route`. `http.error` and `services.cleanup_failed` no longer carry error text; an error reporter that receives the original error is not shipped yet.
- Run `routa generate`, then `routa openapi breaking --update-baseline` once to accept the new response headers into `.routa/openapi-baseline.json`. `routa openapi breaking` reports no breaking change for them.
- A client that reads every response header should expect `x-request-id`.
