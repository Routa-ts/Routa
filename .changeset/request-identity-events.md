Generate a request identity for every request, add opt-in correlation, and replace the automatic request events with safe ones.

- Every request that reaches a Routa app gets a UUID that Routa generates and never takes from the request. Middleware, services factories, and handlers read it as readonly `ctx.requestId`, middleware and handlers log through the readonly request logger `ctx.logger`, every response carries it as `x-request-id`, and it holds for unmatched requests, validation failures, middleware rejects, authentication failures, `406`, automatic `OPTIONS`, `405`, and server errors. A response that a handler on the returned Hono app returns and the runtime cannot copy, such as a `101` upgrade response, goes back unchanged without identity headers, and `http.response.prepared` still records its status. A request that nothing on the returned Hono app answers, not even a middleware after `await next()`, fails as Hono's `500`, or the response of the app's `onError` handler, with identity headers and one event. A Routa app mounted in another with `route()` reuses the outer app's identity, so handlers, headers, and the single event agree, and leaves an unanswered request to the outer app's middleware. It stays with `logger: false`.
- New `correlation` option in `createRouta` and `createHonoApp`: `true` reads `x-correlation-id`, `{ header: "x-trace-ref" }` another header, compared case-insensitively. Routa accepts one value of 1 to 128 ASCII letters, digits, `.`, `_`, or `-`, exposes it as `ctx.correlationId`, binds it to the request logger, and echoes it in the same response header. An absent, empty, repeated, or otherwise invalid value is ignored without rejecting the request. A header that is not a valid name, or that names `x-request-id`, a credential header (`authorization`, `proxy-authorization`, `cookie`, `set-cookie`), or a header Routa writes itself (`content-type`, `content-length`, `transfer-encoding`, `connection`, `allow`, `access-control-allow-methods`, `vary`, `deprecation`, `sunset`, `link`, `www-authenticate`), is rejected at startup and by `routa check`. New types `RequestIdentityContext` and `CorrelationConfig`.
- `ctx.logger` is now a request logger: a child of the configured logger bound to `requestId`, and `correlationId` when accepted, which event data and later `child()` bindings cannot replace and `redact` paths do not redact. Without an accepted correlation ID its events carry no `correlationId`, even when the configured logger's bindings or the event data name one. The configured logger, and every module that imports it, stays without request identity. A request logger configured as another app's logger logs each request that app handles with that request's identity. Services factories receive the same request logger.
- `http.request` is replaced by `http.response.prepared`, written once per prepared response with `requestId`, `correlationId` when present, `method` (a standard method or `_OTHER`), `route` (the route pattern or `[Unmatched]`), `status`, and `durationMs`. It says the response was prepared, not sent. `http.error` now carries `requestId`, `method`, `route`, `status`, and for invalid handler output `issueCount` and the distinct, sorted `issueCodes`, and no longer the request path, issue paths, or any error's message, name, stack, or authentication scheme. `services.cleanup_failed` now carries `failureCount` instead of a `failures` list of error messages, names, and stacks, and the request identity when a request's cleanup failed.
- `requestId`, `correlationId`, and `logger` are reserved context keys like `services`: TypeScript and `routa check` (`ROUTA_CONTEXT_RESERVED`) reject middleware that provides one or passes one to `next()`, registration rejects one in `provides`, and a `next()` payload or assignment that bypasses the types fails the request that reaches it as a `500`. `x-request-id` and the configured correlation header are reserved response headers: TypeScript (for `x-request-id`), `routa check` (`ROUTA_RESPONSE_HEADER_RESERVED`), and registration reject an outcome or reject that declares one, and Routa sets `x-request-id` last on every response, echoes an accepted correlation ID over any other value, and removes the configured correlation header from a response when it accepted none, such as a value a handler forwarded from upstream. It leaves every other header alone.
- `routa check` reads `correlation` from `src/routa.ts` without running it and reports `ROUTA_CORRELATION_CONFIG_UNRESOLVED`, `ROUTA_CORRELATION_HEADER_INVALID`, and `ROUTA_CORRELATION_HEADER_CONFLICT`. Through the type checker, it follows a default that `src/routa.ts` imports or re-exports, such as `export { default } from "./config.js"`, and a spread or config argument bound to an object literal or a `createRouta` call, here or in another module, and reads `correlation`, `services`, and `authentication` there like local members. A `createRouta` call is one to the function `@routa-ts/core` exports, imported under any name, called on a namespace import, or imported from a module that re-exports it; an application function of that name is read by its type. `ROUTA_CORRELATION_CONFIG_UNRESOLVED` also covers any other spread, config argument, computed key, or default export whose type may hold `correlation`, including a value typed `RoutaConfig`; a part whose type has no `correlation` member, such as `{ host: string; port: number }`, is ignored. `.routa/routes.gen.ts` exports `routaCorrelationHeader` when correlation is on, and startup refuses a `src/routa.ts` that disagrees with it.
- Generated OpenAPI documents `x-request-id` on every operation response, and the correlation header as optional when correlation is on. `routa scaffold` and `create-routa-ts` write `x-request-id` into the baselines they create.

Migration:

- Replace `next(ctx)`, which passes the whole context on, with `next()`, or with `next({ ... })` holding only the values the middleware's `provides` declares. `ctx` now holds `requestId`, `correlationId`, and `logger`, which no middleware may pass on, so TypeScript and `routa check` report `next(ctx)` as TS2345, and at runtime the request fails as a `500`.
- Remove middleware that provided `requestId`, `correlationId`, or `logger`, and read `ctx.requestId` instead. To keep a caller-supplied ID, turn on `correlation` and read `ctx.correlationId`; it never replaces the request identity.
- Remove `x-request-id`, and the correlation header if you turn correlation on, from outcome and reject `headers`.
- Update log queries and alerts from `http.request` to `http.response.prepared`, and from `path` to `route`. `http.error` and `services.cleanup_failed` no longer carry error text; send request errors to an error tracker with `onRequestError` instead.
- Run `routa generate`, then `routa openapi breaking --update-baseline` once to accept the new response headers into `.routa/openapi-baseline.json`. `routa openapi breaking` reports no breaking change for them.
- A client that reads every response header should expect `x-request-id`.
