Compose outcomes that share a status, and give middleware rejects the full outcome contract.

- Generated OpenAPI no longer keeps the last schema written for a status. An operation's outcomes are its route `responses` plus the `rejects` of every middleware in its chain, and outcomes that share a status compose into one response. Body outcomes compose when each has a required property with a single string literal value (`z.literal("...")` or a one-value `z.enum([...])`) and the values all differ: the schema becomes a `oneOf` ordered by outcome name with that property as `discriminator.propertyName` (the alphabetically first one when several qualify). Headers declared by several of them project once, `required` only when every outcome requires them; cookies are listed once in `Set-Cookie`. The description lists each outcome's description in outcome-name order as a Markdown list. Nothing depends on source order, and Routa never falls back to `anyOf`.
- `routa check` reports `ROUTA_RESPONSE_STATUS_AMBIGUOUS` for same-status body outcomes without such a discriminator, a body and a bodyless outcome under one status, and several bodyless outcomes under one status; `ROUTA_RESPONSE_HEADER_INCOMPATIBLE` for one header name with different schemas under one status; `ROUTA_RESPONSE_COOKIE_CONFLICT` for one cookie identity from different `createCookie` declarations under one status; and `ROUTA_OUTCOME_NAME_COLLISION` for a route outcome and a reject, or two rejects, that share a name.
- Middleware `rejects` now go through the same `routa check` and OpenAPI reader as route outcomes. Reject `headers` and `cookies` are checked and documented, a reject that `routa check` cannot read (a spread, a computed status or description, an unreadable schema) reports `ROUTA_SCHEMA_UNSUPPORTED` instead of disappearing, a lifecycle-owned reject header reports `ROUTA_RESPONSE_HEADER_LIFECYCLE`, and a reject with a `schema` reachable from a `HEAD` route reports `ROUTA_RESPONSE_BODYLESS_SCHEMA` and fails registration.
- A handler can return only its route's outcomes and a middleware only its own rejects; anything else is invalid handler output. Runtime cookie conflict messages name the producer, such as `middleware[0] reject "expired"`, and `routa check` messages name the middleware behind a reject.
- `next()` now resolves to an opaque `MiddlewareContinuation`, the outcome the rest of the chain selected. A continuing middleware must return it unchanged: TypeScript rejects a copy or added headers and cookies, and returning anything else after `next()`, including one of the middleware's own rejects, fails as invalid handler output.
- TypeScript flags a route outcome named like a reject of the route's own `middleware`, and registration fails for any route outcome and reject, or two rejects, that share a name. The registration message changed from `Duplicate middleware reject key "…"` to `Outcome "…" on … is declared by … and by …`.
- `MiddlewareNext` and `MiddlewareRunArgs` lost their unused `TRejects` type parameter.

Migration: give same-status outcomes a literal discriminator (for example `kind: z.literal("created")`) or distinct statuses. Remove route outcomes that redeclare a middleware reject, such as a route `unauthorized` outcome next to an auth middleware's `unauthorized` reject; the reject is already part of the operation. A middleware that read or changed the result of `await next()` must return that result unchanged; move response decisions into the handler or a reject that returns before `next()`. Drop the `TRejects` argument from explicit `MiddlewareNext<…>` and `MiddlewareRunArgs<…>` references.
