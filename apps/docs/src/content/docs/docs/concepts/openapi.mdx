Routa treats OpenAPI as a projection of the route contract rather than a document you
maintain by hand. It works in both directions: scaffold source from an existing document
once, then generate and check the document from source forever after.

```txt
openapi.yaml/json -> schemas -> route files -> handler stubs   (once, via scaffold)
routes -> OpenAPI -> baseline checks                           (every build)
```

## How It Works

Generation reads validated route metadata and each route file's contract. For every
method it produces an operation containing the parameters and request body from `input`,
a response per entry in `responses`, plus every middleware `rejects` outcome in that
method's chain. An outcome's `description` becomes the response description; without one,
Routa uses the outcome name, so `notFound` becomes "Not found". An outcome without a
`schema` is bodyless and its response has no `content`. An outcome's `headers` become
Header Objects on its response, each with the header's schema, `required` for a required
header, and the schema's `description`. Header schema metadata such as `examples` stays on
the Header Object's schema. An outcome's `cookies` become one standard `Set-Cookie` Header
Object whose description lists each cookie's name and static attributes and says each is a
separate repeated field. The header is `required` when the outcome declares a required cookie,
and the description then names the required cookies. It never carries a value, an example, or a vendor extension.
Middleware `rejects` are documented exactly like route outcomes: description, body, headers,
and cookies. Middleware `openapi` metadata contributes `security` and `x-routa-authz`, and
route `deprecation` metadata marks the operation deprecated.

### Outcomes That Share a Status

OpenAPI has one response per status, so outcomes that share a status are composed into one.
The outcomes considered are the method's own `responses` and the `rejects` of every middleware
in its chain. Composition never depends on the order they are written in:

- Body outcomes compose when every one of them has a required property with a single literal
  value (`z.literal(...)` or a one-value `z.enum(...)`) and those values all differ. The
  response schema becomes a `oneOf` of the outcome schemas, ordered by outcome name, with that
  property as `discriminator.propertyName`. When several properties qualify, the
  alphabetically first name is the discriminator.
- Without such a property, `routa check` fails with `ROUTA_RESPONSE_STATUS_AMBIGUOUS`. Add a
  literal discriminator or give each outcome its own status. Routa never falls back to
  `anyOf`.
- A body outcome and a bodyless outcome cannot share a status, and neither can two bodyless
  outcomes; clients could not tell them apart.
- A header declared by several of the outcomes must have the same schema, metadata included
  (`ROUTA_RESPONSE_HEADER_INCOMPATIBLE`). It is projected once and is `required` only when
  every outcome under the status requires it.
- A cookie identity listed by several of the outcomes must come from the same `createCookie`
  handle (`ROUTA_RESPONSE_COOKIE_CONFLICT`). The `Set-Cookie` description lists it once, as
  always set or cleared only when every outcome requires it.
- The response description lists each outcome's description in outcome-name order, one
  Markdown list item per outcome: ``- `created`: The project was created.``

```ts
responses: {
	created: { status: 201, schema: z.object({ kind: z.literal("created"), id: z.string() }) },
	queued: { status: 201, schema: z.object({ kind: z.literal("queued"), ticket: z.number() }) },
},
```

The `201` response above documents `oneOf: [created, queued]` with
`discriminator: { propertyName: "kind" }`.

The document comes from source alone. Operations, parameters, request bodies, responses,
components, `security`, and generated `operationId` values never come from
`.routa/openapi-baseline.json`, the contract your team has accepted. The baseline is only
what the document is compared against, and nothing is written to it unless you ask.

Every operation gets an `operationId` made from its method and path, so `GET /users/{id}`
is `getUsersId`. The document `info` is always `Routa API` at version `0.0.0`, and no
`servers` are emitted.

## Checking the Contract

```sh
routa openapi check
```

```txt
OpenAPI check passed. No drift detected.
```

`openapi check` fails when an operation, a response status, a parameter, a request body, a
schema (including the content of a component), or an operation's `security` differs from
the baseline. Descriptions, `operationId`, `info`, and `servers` are not compared, except
the generated `Set-Cookie` header description, which lists cookie names and attributes.
Removing a response status or an operation's authentication from source is drift, because the
current document no longer carries them over from the baseline. `openapi breaking` is
narrower: it fails only for removed operations and for inputs that became required or
newly require authentication, so it is the check to run in CI on every pull request.

## OpenAPI to Source

Scaffolding accepts `.yaml`, `.yml`, and `.json` documents and generates route files,
schema modules, and the initial `.routa/` metadata. Generated source is meant to be
reviewed, edited, and committed — Routa does not ask you to trust a generated contract
blindly.

Supported input is deliberately narrow:

- HTTP paths and methods
- `operationId`
- path, query, header, and cookie parameters
- JSON request bodies
- JSON responses
- reusable schemas from `components.schemas`

Anything else stays in the source document untouched rather than being approximated in
TypeScript.

## Generated Extensions

Routa adds three vendor extensions so information that has no standard field is still
visible in the document:

| Extension                 | Meaning                                                         |
| ------------------------- | --------------------------------------------------------------- |
| `x-routa-authz`           | Permission strings declared by middleware `openapi.permissions` |
| `x-routa-diagnostics`     | Validation errors that prevented a complete document            |
| `x-routa-schema-warnings` | Input Routa could not describe, as `ROUTA_SCHEMA_OPAQUE_INPUT`  |

A document containing `x-routa-diagnostics` means generation ran against a project that
does not validate. Fix the diagnostics before trusting the output.

## Limits

Source has no place for a title, version, or `servers` yet, so `info` is a fixed default
and `servers` is omitted. Editing them in the baseline changes nothing, because
`--update-baseline` writes the generated document over it. `components.schemas` comes from the exported and
`.meta({ id })` schemas your routes use; see [Schemas](/docs/concepts/schemas/). The checks
compare schemas by content, so a schema written inline in the baseline and as a `$ref` in
the generated document is not drift. Content types other than JSON are not modeled in v0.

<Aside type="caution" title="Baseline updates">
	`routa openapi breaking --update-baseline` overwrites
	`.routa/openapi-baseline.json` with the current contract. Run it only when the change
	has been reviewed and accepted.
</Aside>

<Aside type="caution" title="v0 status">
	In v0, you can generate OpenAPI, check drift and breaking changes, and scaffold the
	supported JSON contract surface. You cannot use non-JSON content or OpenAPI features
	outside the supported scaffolding list yet.
</Aside>
