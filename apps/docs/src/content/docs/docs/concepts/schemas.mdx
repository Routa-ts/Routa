Routa uses Zod for everything that crosses a boundary: route inputs, middleware inputs,
context values middleware provides, and response payloads. A schema is simultaneously the
runtime validator, the TypeScript type, and the OpenAPI definition.

```ts title="src/routes/users/schemas.ts"
import { z } from "zod";

export const CreateUserSchema = z.object({
	email: z.email(),
	name: z.string().min(1),
});

export const UserSchema = z.object({
	id: z.string(),
	email: z.email(),
	name: z.string(),
});
```

```ts title="src/routes/users/route.ts"
createRoute({
	input: {
		body: CreateUserSchema,
	},
	responses: {
		success: {
			status: 201,
			schema: UserSchema,
		},
	},
	run: async ({ input }) => {
		return { type: "success", data: await users.create(input.body) };
	},
});
```

## How It Works

Routa parses each declared input source with `schema.parse()` before the handler runs, so
`input.body` is the schema's **output** type, not its input type. A schema with a
`transform` or a default gives the handler the transformed value.

On the way out, Routa always checks the result shape, looks up its `type` in the declared
responses, and checks that `data` is present for an outcome with a `schema` and absent for
one without. By default, it parses `data` against the matching response schema in
`routa dev` and compares the parsed value with the value your handler returned. Invalid data,
or any change the schema would make, produces a generic `500` problem response before it
reaches a client. Production parsing and comparison are opt-in with
`responseValidation: "always"`.

Write response schemas to describe wire-ready JSON: they should validate a value, not
change it. `routa check` reports `ROUTA_RESPONSE_SCHEMA_MUTATION` for response schemas that
use `.transform()`, `z.preprocess()`, `.default()`, `.catch()`, `z.coerce.*`, codecs such
as `z.stringbool()`, URL normalization with `z.url({ normalize: true })`, or value-rewriting
checks such as `.trim()`, `.toLowerCase()`, `.toUpperCase()`, `.normalize()`, `.slugify()`,
and `.overwrite()`. The same applies inside `.pipe()` targets, record keys, and
`.check()` arguments, including checks declared in the same file such as
`const tidy = z.trim()`. A `.check()` argument or URL options that Routa cannot read fail
with `ROUTA_SCHEMA_UNSUPPORTED`. Return the final value from the handler instead.

TypeScript rejects schemas whose input and output types differ, and known transformer
wrappers such as `.transform()`, `.default()`, and `z.coerce.*`, when you declare the
outcome. Same-type rewrites such as `.trim()` are visible only to `routa check`, and
`z.url()` trims surrounding whitespace without any marker in source. Runtime validation
catches those: when Routa validates response data, it never sends the parsed value. A
value the schema would change, including an unknown key it would strip, fails as invalid
handler output.

Routa does not parse response data when validation is disabled, so the handler value is
sent as returned. Middleware `provides` schemas remain active in both modes because their
parsed values become downstream context. See
[Configuration](/docs/reference/configuration/) for the full policy.

## How Schemas Become OpenAPI

Routa reads schemas statically from source. It never imports or runs your modules to
generate OpenAPI, so every schema a route uses must be written where Routa can read it:
in the route's sibling `schemas.ts`, in the route file itself, or, for middleware
`rejects`, in the file that declares the middleware. An identifier imported from anywhere
else fails `routa check` with `ROUTA_SCHEMA_UNRESOLVED`.

Composition follows Zod's meaning, not a fixed keyword:

| Zod                                   | OpenAPI 3.1                                               |
| ------------------------------------- | --------------------------------------------------------- |
| `z.union([...])`, `.or()`             | `anyOf`                                                   |
| `z.discriminatedUnion("kind", [...])` | `oneOf` with `discriminator.propertyName: "kind"`         |
| `z.intersection(a, b)`, `.and()`      | `allOf`, or one object when both sides are objects        |
| `z.record(key, value)`                | `additionalProperties`, with key rules in `propertyNames` |
| `.nullable()`                         | `anyOf` with `{ type: "null" }`                           |
| `.optional()`, `.nullish()`           | The property leaves `required`                            |

Input schemas describe what a client sends. A property with `.default()` or `.catch()` is
optional, `z.coerce.number()` is a number, and `.transform()` or `.pipe()` after a readable
schema documents that readable schema. `z.stringbool()` is a `boolean` parameter, following
the OpenAPI convention for `"true"` and `"false"` strings, and a `string` property in a JSON
body. `z.preprocess()` and a leading `z.transform()` run a
function before any schema Routa can read, so `routa check` prints a
`ROUTA_SCHEMA_OPAQUE_INPUT` warning and OpenAPI documents the schema that follows. The
route still runs.

## Documentation Metadata

Zod's `.describe()` and `.meta()` are the documentation interface. Routa copies literal
`title`, `description`, `deprecated`, `example`, `examples`, `readOnly`, `writeOnly`,
`externalDocs`, and `x-` extension keys onto the Schema Object wherever the schema
appears: at the root of a body or response, on a nested property, or in a component.

```ts title="src/routes/users/schemas.ts"
import { z } from "zod";

export const Address = z
	.object({ city: z.string().describe("City name") })
	.meta({ id: "PostalAddress", title: "Address", examples: [{ city: "Lima" }] });

export const UserSchema = z.object({
	id: z.string().meta({ description: "User id", readOnly: true }),
	address: Address,
});
```

Metadata must be a literal Routa can read without running code. Routa reports
`ROUTA_SCHEMA_META_STRUCTURAL` for keys that would override the schema itself, such as
`type` or `default`, `ROUTA_SCHEMA_META_PLACEMENT` for keys that belong to the route, such
as `in` or `operationId`, `ROUTA_SCHEMA_META_COMPUTED` for values computed at runtime, and
`ROUTA_SCHEMA_REGISTRY` for `z.globalRegistry` or `.register()`.

## Where Schemas Live

Route-local schemas in a sibling `schemas.ts` are the default, and scaffolding generates
them that way. When an OpenAPI document declares reusable `components.schemas`, scaffolding
generates a shared module instead and references it from each route.

Exported schema names must be unique within a `schemas.ts` file. Routa reports
`ROUTA_DUPLICATE_SCHEMA_NAME` for repeats. Prefer contract-purpose names like
`CreateUserResponse` over generic ones like `Response`.

An exported schema that a route uses becomes an OpenAPI component named after its export.
`.meta({ id: "PostalAddress" })` names the component explicitly, and an alias such as
`export const GetUserResponse = User` reuses `User`'s component. Schemas declared inline
without an `id` stay inline. Two route directories may each declare an identical `User`
and share one component. If the two declarations differ, or two different declarations
claim the same `id`, Routa reports `ROUTA_SCHEMA_COMPONENT_COLLISION` instead of renaming
either one.

## Query Helpers

Query strings arrive as strings, so common list parameters need a parse step. Routa ships
two helpers for the two most common cases:

```ts title="src/routes/users/schemas.ts"
import { Fields, Sort } from "@routa-ts/core/query/helpers";
import { z } from "zod";

export const ListUsersQuery = z.object({
	sort: Sort(["name", "createdAt"]).optional(),
	fields: Fields(["id", "name", "email"]).optional(),
});
```

`Sort` accepts a field name with an optional `-` prefix and produces
`{ field, direction }`. A request for `?sort=-createdAt` gives the handler
`{ field: "createdAt", direction: "desc" }`, and any field outside the allowed list is
rejected. `Fields` splits a comma-separated list into a validated array, so
`?fields=id,name` becomes `["id", "name"]`. OpenAPI documents both parameters as the
strings clients send.

## Rules

- Validate at the boundary only. A schema describes what the HTTP contract accepts, not
  what your domain considers valid; keep business rules in services.
- Keep response schemas narrow. Anything the schema permits is something a client may
  receive and OpenAPI will advertise.
- Use `responseValidation: "always"` when you need production drift detection.
- Keep response schemas validation-only. Shape the value in the handler.

## Limits

Zod is the only supported schema library in v0, and Routa requires Zod `^4.6.7`. Routa
reads primitives, string formats, `z.literal`, `z.enum` with inline values, `z.object`,
`z.array`, `z.record`, unions, intersections, wrappers such as `.optional()` and
`.nullable()`, checks such as `.min()` and `.refine()`, and metadata. Any other construct,
such as `z.tuple()`, `.extend()`, or a schema built by your own function, fails
`routa check` with `ROUTA_SCHEMA_UNSUPPORTED` instead of producing a guessed or empty
OpenAPI schema. Checks such as `.min()` validate at runtime but are not yet documented as
OpenAPI keywords.

<Aside type="caution" title="v0 status">
	Zod schemas are fully implemented. Adapters for other validation libraries are deferred.
</Aside>
