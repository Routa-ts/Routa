Routa reads its runtime configuration from the default export of `src/routa.ts`. The file
is required — Routa reports `ROUTA_PROJECT_REQUIRED` without it — even when it sets no
options.

```ts title="src/routa.ts"
import { createRouta } from "@routa-ts/core";

export default createRouta({
	host: "127.0.0.1",
	port: 3000,
	lifecycleHeaders: true,
	responseValidation: "always",
});
```

## `host`

```ts
host?: string
```

The interface the server binds to. Defaults to `127.0.0.1`, which accepts local
connections only. Container and platform deployments generally need `0.0.0.0`; set that
through the `HOST` environment variable so local development keeps the safer default.

**Overridden by:** `HOST`.

## `port`

```ts
port?: number
```

The TCP port to listen on. Defaults to `3000`. When the port is unavailable the server
logs `api.start_failed` at `error` level and sets a non-zero exit code.

**Overridden by:** `PORT`.

## `logger`

```ts
logger?: RoutaLogger | false
```

The logger instance used for runtime lifecycle events, request logging, and `ctx.logger`
in every handler. Defaults to `createLogger()`, the built-in console logger at `info`
level.

Set `false` to disable logging entirely. Handlers still receive `ctx.logger`, implemented
as a complete no-op with the same type, so handler code never needs a configuration guard.

```ts title="src/routa.ts"
import { createRouta } from "@routa-ts/core";
import { createLogger } from "@routa-ts/core/logger";

export default createRouta({
	logger: process.env.NODE_ENV === "test" ? false : createLogger({ level: "debug" }),
});
```

Because `RoutaLogger` is a structural type, any object implementing its members is valid,
including an adapter over Pino, Winston, or a hosted logging SDK. See
[Core reference](/docs/reference/core/) for the full member list.

Routa enables logging when a logger is configured. Set `logger: false` to disable it. The
runtime emits two startup lifecycle events and two request events:

| Event              | Level   | Data                                                                    |
| ------------------ | ------- | ----------------------------------------------------------------------- |
| `api.started`      | `info`  | `host`, `port`, `routes`                                                |
| `api.start_failed` | `error` | `error`, `host`, `port`                                                 |
| `http.request`     | `info`  | `method`, `path`, `status`, `durationMs`                                |
| `http.error`       | `error` | `method`, `path`, `status`, `error`, `name`, `stack`, optional `issues` |

With [application services](/docs/concepts/services/), Routa also logs
`services.cleanup_failed` at `error` level, with a `failures` list, when a cleanup callback
throws or rejects.

`http.error` is emitted only for responses with a status of 500 or above. When response
or middleware context validation fails, `issues` contains only Zod `code` and `path`
fields. Routa never logs the rejected response or context values.

## `lifecycleHeaders`

```ts
lifecycleHeaders?: boolean
```

Whether to emit deprecation headers on routes that declare `deprecation`. Defaults to
`false`. When enabled, a deprecated operation responds with:

| Header                                    | Emitted when                         |
| ----------------------------------------- | ------------------------------------ |
| `Deprecation: true`                       | The route declares any `deprecation` |
| `Sunset: <date>`                          | `deprecation.sunset` is set          |
| `Link: <target>; rel="successor-version"` | `deprecation.replacement` is set     |

Routes without `deprecation` are unaffected regardless of this setting. While this is on,
Routa owns those headers on deprecated routes, and an outcome that declares `deprecation`,
`sunset`, or (when a `replacement` is set) `link` in `headers` fails. `routa check` does not run
your code, so it treats any value other than an omitted key or a literal `false` as possibly on
and applies the same ownership rules. Declare a literal `false` to opt a route graph out.

## `responseValidation`

```ts
responseValidation?: "development" | "always"
```

Controls when Routa parses handler responses and middleware reject responses through
their declared Zod schemas and compares the parsed value with the handler value. Defaults to
`"development"`:

| Value           | `routa dev`                     | `routa start`                   |
| --------------- | ------------------------------- | ------------------------------- |
| `"development"` | Parse and compare response data | Do not parse or compare         |
| `"always"`      | Parse and compare response data | Parse and compare response data |

The same policy applies to declared response header values.

Routa always checks the result envelope and response type, requires `data` for an outcome
with a `schema` and rejects it for one without, selects the declared status, checks declared
response headers (names, required headers, and safe values), and performs JSON
serialization. Parsing and comparing fail the response as invalid handler output when
the data does not match its schema or when the schema would change it. Routa never sends the
parsed value. Set `"always"` when production must reject response drift. Response schemas
must not change values; TypeScript rejects the common cases and `routa check` reports
`ROUTA_RESPONSE_SCHEMA_MUTATION` for the rest.

```ts title="src/routa.ts"
import { createRouta } from "@routa-ts/core";

export default createRouta({
	responseValidation: "always",
});
```

This setting does not affect context passed through middleware `provides`. Routa always
parses those values before adding them to downstream context.

## `services`

```ts
services?: ApplicationServicesFactory
```

The application services factory, declared through a `defineServices` helper. Routa runs it
once before the server listens and passes its services to handlers as `ctx.services`.
Omit it to keep every dependency a plain import. See
[Services](/docs/concepts/services/) for the contract rules, cleanup, and
failure behavior.

```ts title="src/routa.ts"
import { createRouta } from "@routa-ts/core";
import { defineAppServices } from "./services.js";

export default createRouta({
	services: defineAppServices(() => ({ clock: { now: () => new Date() } })),
});
```

Declare `services` directly in the `createRouta` object. `routa check` reads it from source,
and startup fails when a spread or a computed config hides it.

## Environment Variables

Environment variables are read at server start and take precedence over `src/routa.ts`.

| Variable | Overrides | Default     |
| -------- | --------- | ----------- |
| `HOST`   | `host`    | `127.0.0.1` |
| `PORT`   | `port`    | `3000`      |

There is no environment override for `logger`, `lifecycleHeaders`, `responseValidation`, or
`services`; branch on your own variables inside `src/routa.ts` instead.

## Precedence

```txt
environment variable  >  src/routa.ts  >  Routa default
```

<Aside type="caution" title="Configuration is read at boot">
	`src/routa.ts` is imported once when the server starts. `routa dev` restarts the process
	on changes under `src/`, so config edits take effect there, but a running `routa start`
	process never re-reads them.
</Aside>
