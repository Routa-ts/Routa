Routa reads its runtime configuration from the default export of `src/routa.ts`. The file
is required — Routa reports `ROUTA_PROJECT_REQUIRED` without it — even when it sets no
options.

```ts title="src/routa.ts"
import { createRouta } from "@routa-ts/core";

export default createRouta({
	host: "127.0.0.1",
	port: 3000,
	lifecycleHeaders: true,
	responseValidation: "always",
});
```

## `host`

```ts
host?: string
```

The interface the server binds to. Defaults to `127.0.0.1`, which accepts local
connections only. Container and platform deployments generally need `0.0.0.0`; set that
through the `HOST` environment variable so local development keeps the safer default.

**Overridden by:** `HOST`.

## `port`

```ts
port?: number
```

The TCP port to listen on. Defaults to `3000`. When the port is unavailable the server
logs `api.start_failed` at `error` level and sets a non-zero exit code.

**Overridden by:** `PORT`.

## `logger`

```ts
logger?: RoutaLogger | false
```

The logger used for runtime lifecycle events, request logging, and `ctx.logger` in every
handler. It must come from [`createLogger`](/docs/reference/core/#createlogger), which
redacts, escapes, and bounds each event before its sink writes it. Without `logger`, Routa
uses `createLogger()`, which writes one JSON line per event to the console at `info` level.

Each request gets its own request logger: a child of this logger bound to the request's
`requestId`, and its `correlationId` when [`correlation`](#correlation) accepted one. Handlers
and route-file and method services factories receive it as `ctx.logger`. Event data and later `child()` bindings
cannot replace those two fields, and the logger you configured stays without them.

Set `false` to disable logging for this application. Handlers still receive `ctx.logger`,
implemented as a complete no-op with the same type, so handler code never needs a
configuration guard. Requests keep `ctx.requestId`, `x-request-id`, and correlation.
`false` changes no logger instance, so a module that imports a shared logger keeps writing
through it.

```ts title="src/routa.ts"
import { createRouta } from "@routa-ts/core";
import { createLogger } from "@routa-ts/core/logger";

export default createRouta({
	logger: process.env.NODE_ENV === "test" ? false : createLogger({ level: "debug" }),
});
```

Routa accepts no other logger object. Loading a `src/routa.ts` whose `logger` is an adapter
or any object `createLogger` did not create fails with a `TypeError` that names the
migration. To keep a backend such as Pino, move the adapter into a
[sink](/docs/reference/core/#sinks):

```ts title="src/logger.ts"
import { createLogger, type RoutaLogSink } from "@routa-ts/core";
import pino from "pino";

const output = pino({ level: "trace" });

const pinoSink: RoutaLogSink = ({ level, event, message, data }) =>
	output[level]({ event, data }, message);

export const logger = createLogger({ level: "info", sink: pinoSink });
```

The [logging guide](/docs/guides/logging/) shows how to share this logger with your services.

### Events Routa Writes

Routa enables logging when a logger is configured. Set `logger: false` to disable it. The
runtime emits two startup lifecycle events and two request events. Request events go through
the request logger, so their data starts with `requestId`, then `correlationId` when present:

| Event                    | Level   | Data                                                                                                |
| ------------------------ | ------- | --------------------------------------------------------------------------------------------------- |
| `api.started`            | `info`  | `host`, `port`, `routes`                                                                            |
| `api.start_failed`       | `error` | `error`, `host`, `port`                                                                             |
| `http.response.prepared` | `info`  | `requestId`, `method`, `route`, `status`, `durationMs`                                              |
| `http.error`             | `error` | `requestId`, `method`, `route`, `status`, `code`, `stage`, and sometimes `issueCount`, `issueCodes` |

`http.response.prepared` is written once for every response Routa prepares, including
unmatched requests, validation failures, middleware rejects, automatic `OPTIONS`, `405`, and
server errors. It records that the response was ready to send, not that it was sent or that
the client received it. A request whose handling fails before any response is prepared logs
no such event. Its fields:

| Field        | Value                                                                                                                      |
| ------------ | -------------------------------------------------------------------------------------------------------------------------- |
| `method`     | `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`, `CONNECT`, or `TRACE` as the request spelled it, else `_OTHER` |
| `route`      | The matched route pattern, such as `/users/:id`, or `[Unmatched]` when no route path matched                               |
| `status`     | The status of the prepared response                                                                                        |
| `durationMs` | Milliseconds from when Routa received the request until the response was prepared, rounded to two decimals                 |

Neither request event includes the request's path, query, raw headers, body, credentials,
principal, or any error's message, name, or stack.

`http.error` is emitted only when a Routa route fails unexpectedly and Routa answers with a
status of 500 or above; a declared outcome with a 5xx status logs only `http.response.prepared`.
Its `code` and `stage` say what kind of failure it was and where it happened, with the values
in the [failure codes and stages](#failure-codes-and-stages) table. When response
or middleware context validation fails, `issueCount` is the number of issues Routa found and
`issueCodes` lists their distinct codes, sorted, such as `["invalid_type"]`. Routa never logs
an issue's path, which can hold request data such as a record key, or the rejected response
or context values.

With [application services](/docs/concepts/services/), Routa also logs
`services.cleanup_failed` at `error` level when a cleanup callback throws or rejects. Its
`failureCount` is how many callbacks failed. Like the request events, it holds no error's
message, name, or stack. For a request's services it goes through the request logger, so it
starts with `requestId`, then `correlationId` when present. `dispose()` still rejects with an
`AggregateError` of the original errors.

## `correlation`

```ts
correlation?: boolean | { header: string }
```

Whether Routa accepts a caller's correlation ID, and from which request header. Off unless
set. `true` reads `x-correlation-id`; `{ header: "x-trace-ref" }` reads another header. Header
names compare case-insensitively. Routa reads the value once at startup, before the services
factory runs, so later changes to the config object have no effect.

Routa accepts the header's value when it is one value of 1 to 128 ASCII letters, digits, `.`,
`_`, or `-`. It then exposes the value as `ctx.correlationId`, binds it to the request logger,
and echoes it in the same response header. An absent, empty, repeated, or otherwise invalid
value is ignored: the request continues, `ctx.correlationId` is `undefined`, and nothing is
echoed or logged. A correlation ID is not authentication and never replaces the request
identity Routa generates.

```ts title="src/routa.ts"
import { createRouta } from "@routa-ts/core";

export default createRouta({
	correlation: { header: "x-trace-ref" },
});
```

```txt
GET /status
x-trace-ref: checkout-42

HTTP/1.1 200 OK
x-request-id: 0b7d4c2e-8f1a-4c6b-9d3e-5a2f1e0c9b8a
x-trace-ref: checkout-42
```

Generated OpenAPI documents the header, so write the value as a literal: `true`, `false`, or
`{ header: "..." }` with a string literal. `routa check` reads it without running
`src/routa.ts`. It follows a default that `src/routa.ts` imports or re-exports, and a spread
or config argument bound to an object literal or a `createRouta` call, here or in another
module, and reads the config there in place. It reports `ROUTA_CORRELATION_CONFIG_UNRESOLVED`
for any other value, and for any other spread, config argument, or computed key whose type
may hold `correlation`, including a value typed `RoutaConfig`. It also
rejects a header name that is not a valid name (`ROUTA_CORRELATION_HEADER_INVALID`) or that
names `x-request-id`, a credential header (`authorization`, `proxy-authorization`, `cookie`,
`set-cookie`), or a header Routa writes itself (`ROUTA_CORRELATION_HEADER_CONFLICT`), so the
echo never replaces one of Routa's headers. Routa writes `content-type`, `content-length`,
`transfer-encoding`, and `connection` on every response; `allow` on automatic `OPTIONS` and
`405` responses; `access-control-allow-methods` and `vary` on automatic `OPTIONS` responses;
the lifecycle headers `deprecation`, `sunset`, and `link`; and `www-authenticate` on
authentication challenges. Startup rejects the same names, and a `src/routa.ts` whose
correlation differs from what `routa generate` recorded.

While correlation is on, Routa owns the configured header on every response: it echoes an
accepted value, removes any value a handler wrote when it accepted none, and rejects an outcome
that declares the header in `headers`.

## `onRequestError`

```ts
onRequestError?: (error: unknown, diagnostic: RequestErrorDiagnostic) => void | Promise<void>
```

Receives each request that fails unexpectedly or breaks its response contract: the value that
was thrown, unchanged, and frozen metadata about the request. Use it to send the error to an
error tracker, which needs the error's message and stack that Routa's logs leave out. Omitted,
nothing is reported. Routa reads the option once at startup and throws a `TypeError` when it is
not a function:

```txt
onRequestError must be a function that receives the original error and its diagnostic. Omit it to report nothing.
```

```ts title="src/routa.ts"
import { createRouta } from "@routa-ts/core";
import { tracker } from "./tracker.js";

export default createRouta({
	// Awaiting the delivery lets Routa contain a delivery that fails.
	onRequestError: async (error, diagnostic) => {
		await tracker.send(error, { tags: diagnostic });
	},
});
```

`tracker` stands for your error tracking client, whose `send` returns a promise. With a client whose capture call returns something else, such as an event ID, call it in a block body instead of returning its result. The callback is a runtime
value: `routa check` and `routa generate` never read or run it, and it does not change generated
OpenAPI.

The diagnostic holds the same facts as the request's `http.error` event:

| Field           | Value                                                                    |
| --------------- | ------------------------------------------------------------------------ |
| `code`          | `unexpected_failure` or `contract_violation`                             |
| `stage`         | Where the request failed, from the table below                           |
| `requestId`     | The request's `x-request-id`                                             |
| `correlationId` | The accepted correlation ID; absent when Routa accepted none             |
| `method`        | The request method, or `_OTHER` for a nonstandard one                    |
| `route`         | The matched route pattern, such as `/orders/:id`                         |
| `status`        | The status of the response Routa chose, which the callback cannot change |

### Failure Codes and Stages

| `code`               | Meaning                                                                                                                                                                                                                                                                                                                                                                                                |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `unexpected_failure` | Application code threw, or Routa failed for a reason it did not expect. The callback receives what was thrown: for an authenticator, extractor, principal schema, services factory, response data `JSON.stringify` throws for, such as a bigint, a circular reference, or a throwing `toJSON()` or getter, or a refinement in a response, header, cookie, or `provides` schema, its own error          |
| `contract_violation` | Application code produced a value its declared contract forbids, such as response data, headers, or cookies that fail the outcome's schema, response data JSON writes no text for, such as `undefined`, a `next()` payload that fails `provides`, or an authenticator result or principal that fails its contract without throwing. The callback receives Routa's error, which describes the violation |

| `stage`          | Where the failure happened                                                                                                              |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `authentication` | Resolving credentials: an authenticator or extractor threw or returned an invalid result                                                |
| `context`        | Building a low-level `createContext` value, including reading the object it returns                                                     |
| `input`          | Reading input, such as a schema refinement that throws instead of reporting an issue                                                    |
| `services`       | A route-file or method services factory                                                                                                 |
| `middleware`     | A middleware callback, including what it passes to `next()` and what it returns                                                         |
| `handler`        | The route handler, including a return value that is not an outcome result at all                                                        |
| `response`       | Checking and serializing the selected outcome, including an outcome type the route does not declare, and its body, headers, and cookies |

A failure is reported once, at the stage where it was first thrown. A handler error that
middleware rethrows keeps the `handler` stage; a different error that middleware throws in its
place is reported, with the `middleware` stage, instead.

Routa does not report expected results: input validation failures (`400`), unsupported media
types (`415`), unacceptable `Accept` headers (`406`), authentication rejections (`401`),
declared outcomes and middleware rejects of any status, unmatched routes (`404`), `405`, and
automatic `OPTIONS`.

The callback sees only what Routa's error mapping answers with a server error, and that mapping
does not change: any `ZodError` that escapes a handler or `createContext` answers `400` and is
not reported, and a request body that cannot be read or parsed, including a body stream that
errors, such as when the client aborts, answers `400` as invalid JSON and is not reported.
Changing those classifications belongs to the future configurable error policy.

Routa chooses the response before it calls the callback and does not await a promise it
returns, so the callback's return value, a throw, or a rejection never changes the response.
Routa calls the callback synchronously, so its synchronous work runs before the response is
returned; do slow work, such as sending to an error tracker, asynchronously. When
the callback throws or rejects, Routa writes one fixed line to `console.error`, once per
application, without either error's text, and never calls the callback for its own failure.
Routa handles a returned promise's rejection the way it handles a logger sink's: through the
built-in `Promise.prototype.then`, so the promise's own `then` never runs. The one rejection it
cannot handle is from a promise subclass whose `constructor`, `Symbol.species`, or species
constructor throws, because the built-in `then` runs them before it attaches a handler; that
rejection can surface as an unhandled rejection, and the failure is still reported:

```txt
{"level":"error","event":"routa.on_request_error.failed","message":"The onRequestError callback threw or rejected. Later failures of this callback in this application are not reported.","timestamp":"2026-01-01T00:00:00.000Z"}
```

The callback runs whether or not logging is on: `logger: false` and a logger level above
`error` silence `http.error`, not the callback. Never pass the error to Routa's logger from the
callback, which would put its text in your logs; send it to your tracker instead. Your
application owns the tracker client, its delivery, and flushing it before the process exits.

Other failures keep their owners and never reach the callback. A configuration or application
services factory that fails at startup rejects `createApplication` and stops `routa start`, and
a server that cannot listen logs `api.start_failed`. A cleanup callback that fails logs
`services.cleanup_failed`, and `dispose()` rejects with its error. An error thrown by a handler
you add to the Hono app goes to Hono's `app.onError()`.

## `lifecycleHeaders`

```ts
lifecycleHeaders?: boolean
```

Whether to emit deprecation headers on routes that declare `deprecation`. Defaults to
`false`. When enabled, a deprecated operation responds with:

| Header                                    | Emitted when                         |
| ----------------------------------------- | ------------------------------------ |
| `Deprecation: true`                       | The route declares any `deprecation` |
| `Sunset: <date>`                          | `deprecation.sunset` is set          |
| `Link: <target>; rel="successor-version"` | `deprecation.replacement` is set     |

Routes without `deprecation` are unaffected regardless of this setting. While this is on,
Routa owns those headers on deprecated routes, and an outcome that declares `deprecation`,
`sunset`, or (when a `replacement` is set) `link` in `headers` fails. `routa check` does not run
your code, so it treats any value other than an omitted key or a literal `false` as possibly on
and applies the same ownership rules. Declare a literal `false` to opt a route graph out.

## `responseValidation`

```ts
responseValidation?: "development" | "always"
```

Controls when Routa parses handler responses and middleware reject responses through
their declared Zod schemas and compares the parsed value with the handler value. Defaults to
`"development"`:

| Value           | `routa dev`                     | `routa start`                   |
| --------------- | ------------------------------- | ------------------------------- |
| `"development"` | Parse and compare response data | Do not parse or compare         |
| `"always"`      | Parse and compare response data | Parse and compare response data |

The same policy applies to declared response header values.

Routa always checks the result envelope and response type, requires `data` for an outcome
with a `schema` and rejects it for one without, selects the declared status, checks declared
response headers (names, required headers, and safe values), and performs JSON
serialization. Parsing and comparing fail the response as invalid handler output when
the data does not match its schema or when the schema would change it. Routa never sends the
parsed value. Set `"always"` when production must reject response drift. Response schemas
must not change values; TypeScript rejects the common cases and `routa check` reports
`ROUTA_RESPONSE_SCHEMA_MUTATION` for the rest.

```ts title="src/routa.ts"
import { createRouta } from "@routa-ts/core";

export default createRouta({
	responseValidation: "always",
});
```

This setting does not affect context passed through middleware `provides`. Routa always
parses those values before adding them to downstream context.

## `services`

```ts
services?: ApplicationServicesFactory
```

The application services factory, declared through a `defineServices` helper. Routa runs it
once before the server listens and passes its services to handlers as `ctx.services`.
Omit it to keep every dependency a plain import. See
[Services](/docs/concepts/services/) for the contract rules, cleanup, and
failure behavior.

```ts title="src/routa.ts"
import { createRouta } from "@routa-ts/core";
import { defineAppServices } from "./services.js";

export default createRouta({
	services: defineAppServices(() => ({ clock: { now: () => new Date() } })),
});
```

`routa check` reads `services` from source: a member of the `createRouta` object, or of a
`const` bound to an object literal or a `createRouta` call, local or imported, that you pass
to `createRouta` or spread into it.
A spread or computed key it cannot read may hide `services` unless a visible `services`
member follows it, so `routa check` warns with
[`ROUTA_SERVICES_SPREAD_UNRESOLVED`](/docs/reference/diagnostics/#routa_services_spread_unresolved).
Startup refuses services that `routa generate` did not read, and generated services that
`src/routa.ts` no longer configures.

## `authentication`

```ts
authentication?: {
	principal: PrincipalSchema;
	schemes: Record<string, CredentialScheme>;
	priority?: readonly string[];
	multipleCredentials?: "priority" | "reject";
}
```

Turns on credential orchestration for every route. Routa reads each request's credentials,
calls one authenticator once, validates the principal it returns, and gives every handler
`ctx.auth`. Omit it and Routa provides no `ctx.auth`: an application without
`authentication` behaves exactly as before, its own middleware may still provide `auth`, and
`requireAuth` fails `routa check`.

| Field                 | Purpose                                                                                                     |
| --------------------- | ----------------------------------------------------------------------------------------------------------- |
| `principal`           | One Zod schema whose output has string `id` and `type` fields. It validates every principal                 |
| `schemes`             | Credential schemes keyed by name. Each name is also the OpenAPI security scheme key                         |
| `priority`            | The order Routa selects among presented credentials. Lists every scheme once. Defaults to declaration order |
| `multipleCredentials` | `"priority"` (default) authenticates the first presented credential by priority. `"reject"` answers `400`   |

Declare schemes with three built-in descriptors, or with `custom` for any other credential.
Each takes the same `authenticate` function and returns the same result shape.

| Descriptor                                                         | Reads                                                       | Challenge       |
| ------------------------------------------------------------------ | ----------------------------------------------------------- | --------------- |
| [`bearer`](/docs/reference/core/#bearer)                           | `Authorization: Bearer <token>`                             | `Bearer`        |
| [`apiKey({ header })`](/docs/reference/core/#apikey)               | The value of one request header                             | `ApiKey`        |
| [`sessionCookie({ cookie })`](/docs/reference/core/#sessioncookie) | The value of one request cookie                             | `Session`       |
| [`custom({ transport, openapi })`](/docs/reference/core/#custom)   | One declared header, `Authorization` auth-scheme, or cookie | The scheme name |

Each scheme needs its own transport. Two Bearer schemes, two API-key schemes whose headers
match ignoring case, two session schemes with the same cookie, an API-key header named
`Authorization` or `Cookie`, and a custom transport another scheme already reads all fail
`routa check` with
[`ROUTA_AUTH_TRANSPORT_OVERLAP`](/docs/reference/diagnostics/#routa_auth_transport_overlap).
Verify several token or key formats inside one authenticator instead. A scheme name starts
with a letter and uses only letters, digits, `.`, `-`, and `_`. A header or cookie name is an
RFC 9110 token: letters, digits, and ``!#$%&'*+-.^_`|~``.

```ts title="src/routa.ts"
import { apiKey, bearer, createRouta, sessionCookie } from "@routa-ts/core";
import { z } from "zod";
import { findServiceKey, findSession, verifyAccessToken } from "./credentials.js";

const Principal = z.discriminatedUnion("type", [
	z.object({ type: z.literal("user"), id: z.string(), email: z.string() }),
	z.object({ type: z.literal("service"), id: z.string() }),
]);

export default createRouta({
	authentication: {
		principal: Principal,
		schemes: {
			userToken: bearer({
				challenge: { realm: "api" },
				authenticate: async (token) => {
					const user = await verifyAccessToken(token);
					return user
						? { type: "authenticated", principal: { type: "user", id: user.id, email: user.email } }
						: { type: "rejected" };
				},
			}),
			serviceKey: apiKey({
				header: "x-api-key",
				authenticate: async (key) => {
					const service = await findServiceKey(key);
					return service
						? { type: "authenticated", principal: { type: "service", id: service.id } }
						: { type: "rejected" };
				},
			}),
			session: sessionCookie({
				cookie: "session",
				authenticate: async (value) => {
					const user = await findSession(value);
					return user
						? { type: "authenticated", principal: { type: "user", id: user.id, email: user.email } }
						: { type: "rejected" };
				},
			}),
		},
		priority: ["userToken", "session", "serviceKey"],
	},
});
```

`verifyAccessToken`, `findServiceKey`, and `findSession` stand for your own verification code,
such as a JWT library call or a session store lookup; Routa verifies nothing itself. TypeScript
checks each authenticator's principal against the principal schema's input, and a rejection
carries no other fields. The second argument holds the configured logger and, when
`src/routa.ts` declares them, the [application services](/docs/concepts/services/).

When a request presents credentials of several schemes, Routa selects the first by `priority`
and calls only that scheme's authenticator. A rejected selected credential fails; Routa never
falls back to the next one. TypeScript rejects a `priority` entry that names no scheme, and
`routa check` also reports a duplicate or missing entry. Set `multipleCredentials: "reject"` to
answer `ambiguousCredentials` (`400`) instead, before any authenticator runs.
[Runtime behavior](/docs/reference/runtime-behavior/#credential-selection) gives the full
selection rules.

`routa check` reads scheme names, descriptor kinds, header and cookie names, custom
transports and `openapi` metadata, challenge overrides, `priority`, and `multipleCredentials`
from source, because they change the HTTP contract. Write `authentication` as an object literal in `createRouta`, or as a `const` object
literal you pass or spread into it, with a plain key for each scheme and a `bearer({ ... })`,
`apiKey({ ... })`, `sessionCookie({ ... })`, or `custom({ ... })` call, or a `const` bound to
one, as its value. Write `header`, `cookie`, `transport`, `openapi`, `priority`, and
`multipleCredentials` as literals. Anything it cannot
read fails with
[`ROUTA_AUTH_CONFIG_UNRESOLVED`](/docs/reference/diagnostics/#routa_auth_config_unresolved).
Authenticators and custom extractors are ordinary runtime functions and may use any
expression. Startup refuses authentication that `routa generate` did not read, and scheme
names, a priority order, or a `multipleCredentials` mode that differ from the generated ones.
Run `routa generate` after changing any of them.
[Runtime behavior](/docs/reference/runtime-behavior/#authentication) describes how each
request's credentials resolve.

## Environment Variables

Environment variables are read at server start and take precedence over `src/routa.ts`.

| Variable | Overrides | Default     |
| -------- | --------- | ----------- |
| `HOST`   | `host`    | `127.0.0.1` |
| `PORT`   | `port`    | `3000`      |

There is no environment override for `logger`, `lifecycleHeaders`, `responseValidation`,
`services`, or `authentication`; branch on your own variables inside `src/routa.ts` instead.

## Precedence

```txt
environment variable  >  src/routa.ts  >  Routa default
```

<Aside type="caution" title="Configuration is read at boot">
	`src/routa.ts` is imported once when the server starts. `routa dev` restarts the process
	on changes under `src/`, so config edits take effect there, but a running `routa start`
	process never re-reads them.
</Aside>
