Routa validates the route graph before TypeScript runs, so contract mistakes surface as
named codes instead of deep inference errors. Every command that touches a project —
`check`, `generate`, `build`, `routes`, `dev`, `start`, and both `openapi` subcommands —
runs the same validation and reports the same codes.

Diagnostics are printed as the code, the file, the message, and a suggestion:

```txt
ROUTA_MIDDLEWARE_ORDER: src/routes/admin/middleware.ts: withAdmin requires ctx.auth before it is provided.
Suggestion: Move middleware that provides auth before withAdmin.
```

Only error diagnostics fail the command. Any error exits with code `1`, and no metadata
is written. A warning is printed with a `Warning:` prefix and does not fail the command
or block the metadata write:

```txt
Warning: ROUTA_SCHEMA_OPAQUE_INPUT: src/routes/imports/schemas.ts: z.preprocess() accepts input Routa cannot describe, so OpenAPI documents the schema after preprocessing: z.preprocess(...)
Suggestion: Parse the incoming value with a declarative schema first, then use .transform() or .pipe() to change it.
```

## Project Structure

### `ROUTA_PROJECT_REQUIRED`

A required file or directory is missing: `package.json`, `tsconfig.json`, `src/`, or
`src/routa.ts`.

**Fix:** run the command from the project root. If you are adding Routa to an existing
project, create `src/routa.ts` with a default `createRouta()` export.

## Route Discovery

### `ROUTA_ROUTE_CONFIG_UNRESOLVED`

The route file has no default export that Routa can statically resolve to a
`createRouteRoot(path)` result.

**Fix:** export the helper call directly. Routa analyzes source without executing it, so
building the config through a variable, a function, or a conditional cannot be resolved.

```ts
// Resolvable
export default route({ get: createRoute({ /* ... */ }) });
```

### `ROUTA_DUPLICATE_ROUTE`

Two route files resolve to the same URL path. The usual cause is a directory-style file
and a flat-style file describing the same path.

**Fix:** rename or move one of them. The message names both files.

### `ROUTA_DUPLICATE_OPERATION_ID`

Two operations would generate the same OpenAPI `operationId`. Routa names each operation
from its method plus the path in PascalCase, treating every run of punctuation as a word
break, so `GET /users/:id` and `GET /users/id` both become `getUsersId`.

**Fix:** change a path segment so the two routes differ by more than punctuation or
parameter syntax, for example `/users/:id` and `/users/by-name`. Routa does not rename an
`operationId` to make it unique.

### `ROUTA_OPTIONS_AUTOMATIC`

A route file declares an `options` method.

**Fix:** remove it. Routa generates `OPTIONS` for every path and keeps its `Allow` header
in sync with the declared methods.

## Contracts

### `ROUTA_MISSING_SUCCESS_RESPONSE`

A method declares no response with a 2xx status.

**Fix:** add one. `204` counts, which is the usual answer for `DELETE`.

### `ROUTA_RESPONSE_INFORMATIONAL_STATUS`

An outcome uses a `1xx` status. Informational statuses are not final responses, so they
cannot be terminal route outcomes.

**Fix:** use a final status from `200` to `599`.

### `ROUTA_RESPONSE_BODYLESS_SCHEMA`

An outcome declares a `schema` but its status is `204`, `205`, or `304`, or it belongs to a
`HEAD` route. None of those responses has a body. A middleware reject reachable from a `HEAD`
route reports this too, at the route file.

**Fix:** remove the `schema`, and return only `{ type }` from the handler or middleware. For a
reject, you can instead keep that middleware off the `HEAD` route.

### `ROUTA_RESPONSE_NOT_MODIFIED_METHOD`

An outcome uses status `304` on a method other than `GET` or `HEAD`.

**Fix:** use a different status, or move the outcome to a `GET` or `HEAD` route.

### `ROUTA_RESULT_TYPE`

A handler returns a `type` that is not declared in its route's `responses`, or a middleware
returns one that is not in its own `rejects`. The message lists the valid names.

**Fix:** correct the name, or declare the outcome.

### `ROUTA_OUTCOME_NAME_COLLISION`

Two outcomes that can end the same operation share a name: a route outcome and a middleware
reject, or the rejects of two middleware in one chain. The handler result names its outcome,
so the names must be distinct.

**Fix:** rename one of them. A route does not need to redeclare a reject its middleware
already declares.

### `ROUTA_RESPONSE_STATUS_AMBIGUOUS`

Outcomes that can end the same operation share a status, and clients could not tell them
apart. Body outcomes need a required property with a single string literal value that
differs in every outcome. A body outcome and a bodyless outcome cannot share a status, and neither can
two bodyless outcomes. Route outcomes and middleware rejects count alike.

**Fix:** add a literal discriminator such as `kind: z.literal("created")` to each body
schema, or give each outcome its own status. See
[Outcomes That Share a Status](/docs/concepts/openapi/#outcomes-that-share-a-status).

### `ROUTA_RESULT_SHAPE`

A returned result object contains a field other than `type`, `data`, `headers`, and `cookies`.

**Fix:** remove the extra field. Results are limited to those four so every response can be
described in OpenAPI. Move anything else into `data`, or declare it as a response header.

### `ROUTA_RESPONSE_HEADER_NAME`

An outcome's `headers` declares a name that is not a valid HTTP header name, or one that is
not lowercase, such as `ETag`.

**Fix:** declare the name in lowercase (`etag`), using only letters, digits, and the
characters allowed in a header name.

### `ROUTA_RESPONSE_HEADER_COLLISION`

An outcome's `headers` declares two names that differ only in case, such as `etag` and
`ETag`. Header identity is case-insensitive and has one owner.

**Fix:** declare the header once, in lowercase.

### `ROUTA_RESPONSE_HEADER_RESERVED`

An outcome's `headers` declares a header Routa owns: `content-type`, `content-length`,
`transfer-encoding`, `connection`, or `set-cookie`.

**Fix:** remove it. Routa sets content headers from the body and the transport. Declare
response cookies as cookies, never as a `set-cookie` header.

### `ROUTA_RESPONSE_HEADER_LIFECYCLE`

An outcome's `headers` declares `deprecation`, `sunset`, or `link` on a route whose
lifecycle headers Routa may write. `routa check` reads `lifecycleHeaders` without running
your code: an omitted key or a literal `false` is off, and any other value, such as
`process.env.LIFECYCLE === "1"`, counts as possibly on. So does a config it cannot read: a
variable, a call, a spread, or a computed key. A default config exported without a local
`createRouta` call, including a re-export, also counts as possibly on. A later literal `false` overrides an earlier
spread, and `createRouta()` with no config is off. `link` is owned only when the route's
`deprecation` names a `replacement`. The deprecation can be an inline object or a local
constant. When it is neither, and the route declares `link`, `routa check` reports
`ROUTA_SCHEMA_UNSUPPORTED` because it cannot tell who owns that header.

**Fix:** remove the header, or set `lifecycleHeaders: false`. If the deprecation is not
readable, write it as an inline object or a local constant.

### `ROUTA_RESPONSE_HEADER_VALUE`

An outcome's `headers` declares a value that is not a string, number, or boolean (or a
literal or enum of them), such as an array or an object. Routa has no multi-value header
support.

**Fix:** declare a string, number, or boolean schema.

### `ROUTA_RESPONSE_COOKIE_UNRESOLVED`

An outcome's `cookies` is not an array literal of identifiers, or of
`{ handle, required: true }` entries, that resolve to a `createCookie({ ... })` declaration.
Routa follows identifiers declared in the route file or its `schemas.ts`, and relative imports
and re-exports: `export const`, `export { name }`, aliases, `export { name } from`, and
`export * from`. It does not follow package imports, aliases of other variables, or spreads.

**Fix:** list handles by name, write a required one as `{ handle: session, required: true }`,
and declare each handle with `createCookie` in a module the route imports by relative path.

### `ROUTA_RESPONSE_COOKIE_STATIC`

A `createCookie` call writes its name or an attribute as something other than a literal, or
spreads another object. A required cookie entry in `cookies` must also be a literal, with
`required: true`. Cookie names and attributes are contract facts that `routa check` and
OpenAPI read without running your code.

**Fix:** write each name and attribute as a literal inside `createCookie({ ... })`.

### `ROUTA_RESPONSE_COOKIE_ATTRIBUTE`

A `createCookie` call omits `httpOnly`, `secure`, `sameSite`, `path`, or `schema`, or gives an
attribute a value it cannot have, such as a negative `maxAge`, a `path` without a leading `/`,
with a trailing space, or with characters outside printable ASCII (write those percent-encoded),
or an `expires` that is not an ISO 8601 date-time.

**Fix:** declare the required attributes and correct the value.

### `ROUTA_RESPONSE_COOKIE_NAME`

A cookie name is not an RFC 6265 token: it is empty or contains a space, `;`, `,`, `=`, or
another separator.

**Fix:** use letters, digits, and the characters ``! # $ % & ' * + - . ^ _ ` | ~``.

### `ROUTA_RESPONSE_COOKIE_RULE`

A cookie breaks a security rule: `sameSite: "none"` or `partitioned: true` without
`secure: true`, a `__Secure-` name without `secure: true`, or a `__Host-` name without
`secure: true`, with a `path` other than `/`, or with a `domain`.

**Fix:** set `secure: true`, and for `__Host-` cookies use `path: "/"` and remove `domain`.

### `ROUTA_RESPONSE_COOKIE_VALUE`

A cookie's value schema is not a string, number, or boolean (or a literal or enum of them).
A value schema that changes values reports `ROUTA_RESPONSE_SCHEMA_MUTATION` instead.

**Fix:** declare a scalar schema that validates the value without changing it.

### `ROUTA_RESPONSE_HEADER_INCOMPATIBLE`

Outcomes that share a status declare one header name with different schemas or metadata.
OpenAPI documents one Header Object per name for the status.

**Fix:** declare the header the same way in each outcome, or use distinct statuses.

### `ROUTA_RESPONSE_COOKIE_CONFLICT`

An outcome's `cookies` lists the same handle twice, or two handles with one identity (name,
domain, and path). One producer owns an identity in a response. Outcomes that share a status
also report this when they list one identity from different `createCookie` declarations.

**Fix:** list the cookie once, share one handle between the outcomes, or give the handles
different names, domains, or paths.

### `ROUTA_RESPONSE_COOKIE_SCOPE`

An outcome declares cookies with one name and different domains or paths. This is a warning:
browsers keep them apart, but clients and readers often confuse them.

**Fix:** rename a cookie unless the different scopes are intended.

### `ROUTA_DUPLICATE_SCHEMA_NAME`

A `schemas.ts` file exports two schemas with the same name. Exported schema names become
OpenAPI component names. Across files, identical declarations with the same name share a
component, and different ones fail with `ROUTA_SCHEMA_COMPONENT_COLLISION`.

**Fix:** rename one to something contract-specific, such as `CreateUserResponse`.

## Middleware

### `ROUTA_MIDDLEWARE_ORDER`

A middleware requires a context key that nothing earlier in the chain provides.

**Fix:** move the providing middleware earlier. Chain order is folder middleware, then
route-level, then method-level, and within a `middleware.ts` file it is export order.

### `ROUTA_MIDDLEWARE_REJECT_STATUS`

A middleware `rejects` entry uses a status outside the 4xx and 5xx ranges.

**Fix:** use an error status. A middleware that needs to return a success response is a
handler concern, not a reject.

### `ROUTA_MIDDLEWARE_UNRESOLVED`

A middleware reference could not be resolved statically, usually because the array spreads
another array or computes an entry.

**Fix:** list each middleware as a direct identifier of a `createMiddleware` export.
Unresolvable middleware would run without contract checks, so Routa refuses it.

## Deprecation

### `ROUTA_DEPRECATION_REPLACEMENT_ROUTE_NOT_FOUND`

`deprecation.replacement` starts with `/` but does not match a route in this project.

**Fix:** correct the path, or run `routa generate` if the target route is new and metadata
is stale.

### `ROUTA_DEPRECATION_REPLACEMENT_URL_INVALID`

`deprecation.replacement` is neither a local path beginning with `/` nor an absolute
`http:` or `https:` URL.

**Fix:** use `/new-route` for this API, or `https://api.example.com/new-route` for another.

## Schemas

Routa reads route and middleware schemas statically to check them and to generate OpenAPI.
These codes name the schemas it cannot read faithfully. See
[Schemas](/docs/concepts/schemas/) for what is supported.

### `ROUTA_SCHEMA_UNSUPPORTED`

A schema uses a construct Routa cannot describe in OpenAPI, such as `z.tuple()`,
`.extend()`, `z.date()`, a schema built by calling your own function, or a value that is
not a Zod schema. Route `input` also needs static `params`, `query`, `headers`, `cookies`,
or `body` properties, not a spread or a shared variable, and each outcome in `responses`
needs a literal `status` and a `schema` written in place, not spread in.

In response schemas, Routa also reports a `.check()` argument it cannot classify, such as
a check built by your own function, and URL options whose `normalize` value it cannot read.

**Fix:** write the schema with supported Zod constructs. Compose objects with
`z.intersection()` or `.and()`, and describe dates on the wire with `z.iso.datetime()` or
`z.iso.date()`. Pass `.check()` a Zod check such as `z.minLength(1)` or an inline function,
and write URL options as an object literal.

### `ROUTA_SCHEMA_UNRESOLVED`

A schema identifier does not name a declaration Routa can read. Routa reads route schemas
from the route file and its sibling `schemas.ts`, and middleware reject schemas from the
file that declares the middleware. It does not follow imports.

**Fix:** declare or export the schema in one of those files.

### `ROUTA_RESPONSE_SCHEMA_MUTATION`

A response schema changes the value it validates, for example with `.transform()`,
`.default()`, `z.coerce.number()`, `.trim()`, `.check(z.trim())`,
`z.url({ normalize: true })`, or a record key such as `z.string().toLowerCase()`.

**Fix:** return the wire-ready value from the handler and keep the response schema
validation-only.

### `ROUTA_SCHEMA_OPAQUE_INPUT`

Warning. An input schema runs a function before any schema Routa can read, through
`z.preprocess()` or a leading `z.transform()`. The route still runs, and OpenAPI documents
the schema that follows the function.

**Fix:** parse the incoming value with a declarative schema first, then change it with
`.transform()` or `.pipe()`, or accept the warning.

### `ROUTA_SCHEMA_META_STRUCTURAL`

`.meta()` sets a key that would override the schema's structure, such as `type`,
`properties`, `format`, or `default`.

**Fix:** express the constraint with the Zod schema and keep `.meta()` for documentation.

### `ROUTA_SCHEMA_META_PLACEMENT`

`.meta()` sets a key that places the schema in a route, such as `in`, `param`, or
`operationId`.

**Fix:** put the schema under `input` or `responses` in `createRoute`.

### `ROUTA_SCHEMA_META_UNSUPPORTED`

`.meta()` sets a key Routa does not document.

**Fix:** use `id`, `title`, `description`, `deprecated`, `example`, `examples`,
`readOnly`, `writeOnly`, `externalDocs`, or an `x-` extension.

### `ROUTA_SCHEMA_META_COMPUTED`

Metadata is computed at runtime, for example `.describe(label)` or a spread in `.meta()`.

**Fix:** write metadata as inline literals.

### `ROUTA_SCHEMA_REGISTRY`

A schema file uses `z.globalRegistry`, `z.registry()`, or `.register()`, including
`globalRegistry` or `registry` imported by name from `zod`. Registry metadata lives outside
the route contract.

**Fix:** attach documentation with `.meta()` or `.describe()` on the schema the route uses.

### `ROUTA_SCHEMA_COMPONENT_COLLISION`

One `components.schemas` key would hold two different schemas. This happens in two cases:

- Two different declarations share a key: two `.meta({ id })` calls with the same id, or two
  exports with the same name and different content.
- One declaration projects differently in different places, for example input and output, or
  a query parameter and a JSON body. A schema such as `z.stringbool()` has a different shape
  in each, so it cannot be one component.

**Fix:** for two declarations, reuse one declaration, or give each a distinct
`.meta({ id })`. For one declaration with different projections, write separate declarations
with distinct component identities, or change the schema so every use projects the same way.
Routa never renames components or picks one projection.

### `ROUTA_SCHEMA_COMPONENT_ID_INVALID`

A schema `id` or export name used as a component key contains characters OpenAPI does not
allow.

**Fix:** use only letters, digits, `.`, `-`, and `_`.

## OpenAPI

### `ROUTA_OPENAPI_UNSUPPORTED_EXTENSION`

`routa scaffold` received a file that is not `.yaml`, `.yml`, or `.json`.

### `ROUTA_OPENAPI_FILE_NOT_FOUND`

The OpenAPI file path does not exist relative to the project root.

## Scaffolding

### `ROUTA_SCAFFOLD_UNMANAGED_FILE`

A file already exists where scaffolding wants to write, and `.routa/manifest.json` does not
track it.

**Fix:** move or rename your file. If Routa did generate it and the manifest was lost,
restore the manifest from version control.

### `ROUTA_SCAFFOLD_MODIFIED_GENERATED_FILE`

A tracked generated file no longer matches its recorded hash, or its manifest hash is
missing. Routa refuses to overwrite or remove it because local edits may be lost.

**Fix:** move the edits into application-owned modules, then regenerate. Run with
`--preview` first to see the full list. If the hash is missing, restore
`.routa/manifest.json` from version control before regenerating.

## Non-Coded Failures

Some conditions fail without a `ROUTA_*` code because they are detected at registration or
in the OpenAPI commands rather than during route validation:

| Message                                                           | Meaning                                                    |
| ----------------------------------------------------------------- | ---------------------------------------------------------- |
| `Missing .routa/openapi-baseline.json. Run routa scaffold first.` | No accepted contract exists yet                            |
| `Regeneration requires preview or confirmation.`                  | Scaffolding again without `--preview` or `--yes`           |
| `Outcome "…" on … is declared by … and by …`                      | A route outcome and a reject, or two rejects, share a name |
| `Duplicate route registration: …`                                 | The same method and path registered twice at runtime       |
| `Middleware requires ctx.… but it was not provided.`              | A required context key was missing at request time         |
| `Missing compiled runtime output for …`                           | `routa start` without a current `routa build`              |

<Aside type="note" title="Generated documents carry diagnostics">
	When OpenAPI generation runs against a project that does not validate, the output
	contains `x-routa-diagnostics` with the same codes instead of a partial contract. Fix
	the diagnostics before trusting the document.
</Aside>
