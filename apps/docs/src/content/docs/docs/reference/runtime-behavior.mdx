Routa v0 runs on Hono. This page documents the request pipeline, every status Routa
produces on its own, and the shape of its error responses. Behavior described here comes
from `createHonoApp` and applies to `routa dev`, `routa start`, and any app you build
directly.

## Request Pipeline

Before anything else, every request that reaches the app gets its
[request identity](#request-identity), whether or not a route matches it. Then, for each
matched route, in order:

1. **Credential resolution.** Only when `src/routa.ts` configures
   [`authentication`](/docs/reference/configuration/#authentication). Routa reads the request's
   credentials and sets `ctx.auth`, or ends the request with `authenticationFailed` or, in
   strict mode, `ambiguousCredentials`. See [Authentication](#authentication).
2. **Accept negotiation.** A request whose `Accept` header cannot be satisfied by JSON
   receives `406 Not Acceptable`. A missing `Accept` header is treated as acceptable.
3. **Input parsing.** Declared `params`, `query`, `headers`, `cookies`, and `body` are
   parsed with their Zod schemas. The body is read at most once per request and shared
   between middleware and the handler.
4. **Context creation.** `createContext()` runs if provided. It must return a plain
   object.
5. **Middleware chain.** Each middleware's `requires` keys are checked against the current
   context, then `run` executes. It either returns one of its own rejects, ending the request,
   or calls `next()`, or `next({ ... })` with the values its `provides` declares, and returns
   what `next()` resolves to, unchanged. Returning anything else after `next()` fails as
   invalid handler output. Declared `provides` values are parsed before any are merged, and
   undeclared top-level keys are omitted.
6. **Handler.** `run` receives the parsed input and the accumulated context, with
   framework-owned values such as `logger`, `requestId`, and `correlationId` applied last so
   they cannot be replaced.
7. **Response validation.** As soon as the handler or a middleware returns an outcome, before
   earlier middleware resume, the result shape and `type` are checked against the
   outcomes of whoever returned it: the route's `responses` for the handler, or that
   middleware's own `rejects`. Its `data` is parsed according
   to the configured response-validation policy. Declared headers and cookie effects are
   checked the same way. A missing required cookie effect fails in every mode.
8. **Serialization.** The response is written at the same point as
   `application/json; charset=utf-8`, with the outcome's declared headers, its cookies as
   repeated `Set-Cookie` fields, and, when enabled, lifecycle headers. A bodyless outcome gets
   no content headers. The selected response is then fixed: changes that code makes later to
   the objects the result was built from do not reach the client.
9. **Identity headers.** Once any response is prepared, Routa sets `x-request-id` over
   anything else that wrote it. With correlation on, it sets the configured correlation header
   to the accepted correlation ID, or removes that header when it accepted none. Then it logs
   `http.response.prepared`.

## Request Identity

Routa generates a UUID for every request it receives and never takes one from the request.
Handlers, middleware, and route-file and method services factories read it as `ctx.requestId`, every response
carries it as `x-request-id`, and every event the request logger writes includes it. The same
holds for unmatched requests, validation failures, middleware rejects, authentication
failures, `406`, automatic `OPTIONS`, `405`, and server errors.

```txt
GET /status
x-request-id: client-chosen

HTTP/1.1 200 OK
x-request-id: 3c9e1f7a-2b4d-4e8f-a6c5-9d0b1e2f3a4b
```

With [`correlation`](/docs/reference/configuration/#correlation) on, Routa also accepts one
valid correlation ID from the configured header, exposes it as `ctx.correlationId`, binds it to
the request logger, and echoes it. Without a valid value the header is absent from the
response, even when a handler wrote one, such as a value forwarded from an upstream service.
Routa owns only that header and `x-request-id`; it leaves every other header a handler writes
alone. A correlation ID associates requests across systems; it is not authentication and not
tracing identity.

Routa owns these values:

- `ctx.requestId` and `ctx.correlationId` are readonly. Middleware cannot declare them in
  `provides` or pass them to `next()`, and cannot assign them; `ctx.logger` is reserved the same
  way. TypeScript and `routa check` (`ROUTA_CONTEXT_RESERVED`) reject each case, and route
  registration rejects a reserved key in `provides`. A `next()` payload or an assignment that
  bypasses the types fails the request that reaches it as a `500`.
- An outcome or reject cannot declare `x-request-id`, or the configured correlation header, in
  `headers` (`ROUTA_RESPONSE_HEADER_RESERVED`).
- The request logger keeps `requestId` and `correlationId` whatever event data or `child()`
  bindings name them, and never redacts them, even when the configured logger's `redact` paths
  name them, so logs and response headers carry the same identity. When Routa accepted no correlation ID, its events and bindings have no
  `correlationId` at all, even if the configured logger's bindings or the event data name one.
  The logger you configured, and any module that imports it, stays without request identity,
  so concurrent requests never share it. When you configure a request logger, such as
  `ctx.logger`, as another app's logger, that app's events carry the identity of the request
  it is handling, not the identity the logger was bound to.

A handler you add to the Hono app `createHonoApp` returns can return any `Response`. Routa
writes its headers on a copy of a response it did not prepare, so a response your code reuses
or one with immutable headers never carries another request's identity. A response the runtime
cannot copy is the exception: the `Response` constructor accepts only statuses `200` to `599`,
so a `101 Switching Protocols` upgrade response, such as the one `Deno.upgradeWebSocket()`
returns, goes back unchanged, without `x-request-id` or the correlation echo, and with any
correlation header it already carries. `http.response.prepared` still records it with status
`101`.

An error thrown by a handler you add to that Hono app goes to Hono's error handler, because the
handler is your Hono code rather than a Routa route. Hono's default handler answers an
`HTTPException` with its own response and prints nothing. For any other error it prints the
error, including its message and stack, to the console and answers `500 Internal Server Error`.
Either response carries `x-request-id` and is logged once as `http.response.prepared` with its
status, without an `http.error` event, and
[`onRequestError`](/docs/reference/configuration/#onrequesterror) is not called. Set
`app.onError()` to decide what such failures print, report, and return.

A handler or middleware you add that neither returns a response nor calls `next()` leaves the
request unanswered. Hono fails such a request through its error handler only after the whole
chain returns, where Routa cannot reach the response. Routa raises the same error, `Context is
not finalized`, inside the chain instead, so Hono's default `500 Internal Server Error`, or the
response of a handler you set with `app.onError()`, carries `x-request-id` and is logged once
with its status. Routa raises it only after every middleware you added has returned, so a
middleware that answers after `await next()` still supplies the response, and that response
carries the identity.

When you mount one Routa app in another with `outer.route("/api", inner)`, both built by
`createHonoApp`, the request is identified once, by the outer app. Handlers in the inner app
see the same `ctx.requestId` and `ctx.correlationId`. Only the outer app sets the identity
headers and logs `http.response.prepared`, through its logger, with the route pattern the inner
app declares, such as `/whoami`, without the mount prefix. The inner app's request logger still
writes to the inner app's logger, bound to the same identity. Only the outer app fails an
unanswered request, so outer middleware that answers after `await next()` can answer for the
inner app. A Routa app mounted in a plain Hono app owns the request instead, so it fails an
unanswered request before the host app's middleware returns; answer such requests inside the
Routa app. Hono's `route()` also changes a mounted app that sets its own `app.onError()`: it
wraps each of that app's handlers and finalizes an unanswered request as an empty `200`, which
Routa then identifies and logs with that status. Answer every request inside an app that sets
`onError()` before you mount it.

Give a mounted Routa app the same `correlation` setting as the app you mount it in: both off,
or the same header name in any casing. Each app checks its correlation header only against its
own credential schemes and declared response headers, so only the same setting lets those checks
cover the mounted app. When the settings differ, the mounted app answers every request that
reaches it, whether a Routa route, a Hono handler you added to it, or nothing would answer it,
with Routa's internal `500` problem, logged with the `[Unmatched]` route. The response keeps its `x-request-id`, and the outer app
neither echoes nor logs a correlation ID for it, so a credential the mounted app reads from that
header never reaches the response or the logs. The mounted app logs `http.error` and calls its `onRequestError` with
`code` `configuration_error` and `stage` `identity`. The error it passes names both settings and
holds no header value.

## Status Codes Routa Produces

| Status | Cause                                                                                 |
| ------ | ------------------------------------------------------------------------------------- |
| `204`  | Automatic `OPTIONS` response                                                          |
| `400`  | Input failed schema validation, or the JSON body could not be parsed                  |
| `400`  | Strict mode received credentials of several accepted schemes (`ambiguousCredentials`) |
| `401`  | A presented credential failed authentication (`authenticationFailed`)                 |
| `401`  | A `requireAuth` guard received an anonymous request (`authenticationRequired`)        |
| `404`  | No route matches the request path                                                     |
| `405`  | The path exists but does not declare the requested method                             |
| `406`  | The `Accept` header cannot be satisfied by JSON                                       |
| `415`  | The request body's content type is not a JSON media type                              |
| `500`  | A handler or middleware returned output that does not match its contract              |
| `500`  | A route-file or method service factory failed during the request                      |
| `500`  | A handler or middleware threw an error it did not handle                              |
| `500`  | An authenticator threw, or returned a result or principal that breaks its contract    |
| `500`  | A mounted Routa app's `correlation` setting differs from the app it is mounted in     |

Every other status comes from your contract: a handler outcome or a middleware reject.

## Error Response Shape

For most errors Routa generates, it returns problem documents. Responses with status 404,
405, or 406 are the plain-text exceptions, and their body is the text in the Title column of
the table below:

```json
{
	"type": "https://routa-ts.dev/problems/validation",
	"title": "Validation failed",
	"status": 400,
	"issues": [{ "path": ["body", "email"], "message": "Invalid email address" }]
}
```

| `type`                               | Title                   | Status |
| ------------------------------------ | ----------------------- | ------ |
| `…/problems/validation`              | Validation failed       | 400    |
| `…/problems/invalid-json`            | Invalid JSON body       | 400    |
| `…/problems/ambiguous-credentials`   | Ambiguous credentials   | 400    |
| `…/problems/authentication-failed`   | Authentication failed   | 401    |
| `…/problems/authentication-required` | Authentication required | 401    |
| Plain text (no problem type)         | 404 Not Found           | 404    |
| Plain text (no problem type)         | Method Not Allowed      | 405    |
| Plain text (no problem type)         | Not Acceptable          | 406    |
| `…/problems/unsupported-media-type`  | Unsupported Media Type  | 415    |
| `…/problems/handler-output`          | Invalid handler output  | 500    |
| `…/problems/internal`                | Internal Server Error   | 500    |

Only input validation problems include `issues` in the response. Handler-output problems
never leak the underlying message or response values, since they may contain internal
data.

## Authentication

When `src/routa.ts` configures [`authentication`](/docs/reference/configuration/#authentication),
Routa resolves every matched request's credentials before anything else reads the request.
Each scheme reads its own transport:

| Scheme          | Presented when                                                                                         | Malformed, so its authenticator does not run                                                                                         |
| --------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| `bearer`        | `Authorization` names the `Bearer` scheme                                                              | The token is empty or not an RFC 6750 `b64token`                                                                                     |
| `apiKey`        | The configured header is present                                                                       | The value is empty, or holds a comma, as a repeated header does                                                                      |
| `sessionCookie` | The `Cookie` header carries the configured name                                                        | The value is empty, or the cookie appears more than once                                                                             |
| `custom`        | Its header is present, its `Authorization` auth-scheme matches ignoring case, or its cookie is present | The value is empty, a header value holds a comma, or the cookie appears more than once; or `extract` returns `{ type: "malformed" }` |

`Headers` joins a repeated header into one value separated by `, `, so Routa cannot tell a
repeated API-key header from a key that holds a comma. Both fail. A session cookie value is
percent-decoded the same way as declared `cookies` input. An `Authorization` header that no
configured scheme reads, such as `Basic …` without a custom scheme for `Basic`, `Bearer …`
without a Bearer scheme, or `Bearer` followed by a tab instead of spaces, is an unsupported
credential. A custom transport `{ header: "authorization" }` without a `scheme` reads every
`Authorization` header, so none is unsupported.

A custom scheme's `extract` runs only for a selected, well-formed credential, receives the
value alone, and returns before the authenticator runs. The authenticator runs at most once
per request. Routa parses an accepted principal once with
the principal schema, and `ctx.auth.principal` is the schema's output. `ctx.auth` is readonly:
middleware cannot replace it, and writing it fails the request with the generic `500`.

A [`requireAuth`](/docs/reference/core/#requireauth) guard runs at its position in the
middleware chain, after input parsing. A guard a folder `middleware.ts` exports runs with the
folder's middleware, before route and method middleware. It returns `authenticationRequired`
for an anonymous request and passes an authenticated one on. The handler sees the authenticated branch of
`ctx.auth`. Startup refuses a folder `middleware.ts` that exports a `requireAuth` guard the
generated metadata does not list, because Routa would never run it; see
[Authentication Requirements](/docs/concepts/middleware/#authentication-requirements).

### Credential Selection

Each operation accepts a set of schemes, which Routa computes once at startup: the schemes
every `requireAuth` guard in its middleware chain allows, from the root folder to the method,
or every configured scheme when no guard applies. Only credentials of accepted schemes are eligible. For each request:

| Presented credentials                                   | Result                                                |
| ------------------------------------------------------- | ----------------------------------------------------- |
| None                                                    | `ctx.auth` is `{ status: "anonymous" }`               |
| Only unsupported, or only of schemes not accepted       | `authenticationFailed`; no authenticator runs         |
| Exactly one eligible, in either mode                    | It is selected                                        |
| Two or more eligible, `multipleCredentials: "priority"` | The first eligible by `priority` is selected          |
| Two or more eligible, `multipleCredentials: "reject"`   | `ambiguousCredentials` (`400`); no authenticator runs |

Routa then checks the selected credential. A malformed one fails without calling the
authenticator. Otherwise the scheme's authenticator alone runs: an accepted principal makes
`ctx.auth` `{ status: "authenticated", scheme, principal }`, and a rejection returns
`authenticationFailed`. Routa never falls back to another credential, and a presented
credential that fails never downgrades to anonymous, on public operations and protected ones
alike. Because resolution runs first, a request it fails receives `authenticationFailed` or
`ambiguousCredentials` whatever its `Accept` header or body.

A credential of a scheme the operation does not accept never authenticates it. A route behind
`requireAuth({ schemes: ["session"] })`, inline or inherited from a folder, that receives only
a valid Bearer token returns `authenticationFailed`, challenging `Session`, and the Bearer
authenticator never runs. When the same request also carries a session
cookie, Routa ignores the Bearer token and authenticates the session.

### Outcomes and Challenges

Both `401` outcomes are problem documents with a `WWW-Authenticate` challenge:

```json
{
	"type": "https://routa-ts.dev/problems/authentication-failed",
	"title": "Authentication failed",
	"status": 401
}
```

Each scheme's challenge names its auth-scheme, `Bearer`, `ApiKey`, `Session`, or for a
custom scheme its name or the override's `scheme`, with `realm="…"` when the scheme declares a
static [challenge override](/docs/reference/core/#bearer):

| Situation                                    | Outcome                  | `WWW-Authenticate`                                       |
| -------------------------------------------- | ------------------------ | -------------------------------------------------------- |
| No credential behind `requireAuth`           | `authenticationRequired` | Every accepted scheme, in priority order                 |
| Only unsupported or not-accepted credentials | `authenticationFailed`   | Every accepted scheme, in priority order                 |
| Malformed or rejected Bearer token           | `authenticationFailed`   | `Bearer error="invalid_token"`, with the realm first     |
| Malformed or rejected API key or session     | `authenticationFailed`   | That scheme alone: `ApiKey` or `Session`, with its realm |
| Malformed or rejected custom credential      | `authenticationFailed`   | That scheme alone, such as `Basic realm="api"`           |

Several challenges share one header, such as `Bearer realm="api", Session`. Routa adds
`error="invalid_token"` to Bearer challenges only, and never adds `error_description`,
`error_uri`, or any value from the request, the application, or its provider.

In strict mode, `ambiguousCredentials` is a `400` problem document without a challenge, since
the client already holds credentials and must send one:

```json
{
	"type": "https://routa-ts.dev/problems/ambiguous-credentials",
	"title": "Ambiguous credentials",
	"status": 400
}
```

It applies only to operations that accept two or more schemes. On an explicit `HEAD`
operation every authentication outcome keeps its status and challenge without a body.

### Authenticator Failures

| Authenticator behavior                                                                                | Response                                            |
| ----------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| Returns `{ type: "rejected" }`                                                                        | `401` `authenticationFailed`                        |
| Throws                                                                                                | `500` `…/problems/internal`                         |
| Returns a principal the principal schema rejects, or parses to a value without string `id` and `type` | `500` `…/problems/internal`                         |
| Returns anything other than `authenticated` or `rejected`                                             | `500` `…/problems/internal`                         |
| Returns a result whose `type` throws when read, or a principal whose parsing or parsed fields throw   | `500` `…/problems/internal`                         |
| A custom `extract` returns `{ type: "malformed" }`                                                    | `401` `authenticationFailed`; no authenticator runs |
| A custom `extract` throws, or returns neither `credential` nor `malformed`, such as a promise         | `500` `…/problems/internal`; no authenticator runs  |

An invalid result is an application contract violation, not a client error: `http.error`
records it with `code` `contract_violation` and `stage` `authentication`. When an
authenticator or extractor throws, or a getter or principal schema step throws while Routa reads
the result, `http.error` carries only the request identity, method, route, status, `code`
`unexpected_failure`, and `stage` `authentication`: never the scheme or the thrown value, which
may carry the credential. Only [`onRequestError`](/docs/reference/configuration/#onrequesterror)
receives the thrown value. A thrown error stays a server error so an outage at a provider never
reads as a bad credential.

## Methods

Applications declare `get`, `post`, `put`, `patch`, `delete`, and optionally `head`.

- **`OPTIONS` is automatic.** Every known path answers `OPTIONS` with `204` and an `Allow`
  header derived from that path's methods, including the implicit `HEAD` for `GET` and
  `OPTIONS` itself. Declaring `options` is a registration error.
- **`HEAD` is implicit for `GET`.** Declare `head` explicitly only when it needs its own
  contract; explicit `HEAD` contracts are registered ahead of `GET` so they win without
  intercepting real `GET` requests.
- **`GET` and `HEAD` cannot declare a body.** Registration throws.
- **Unsupported methods return `405`** with the same `Allow` header.

## CORS Preflight

A preflight carrying both `Origin` and `Access-Control-Request-Method` receives the derived
method list as `Access-Control-Allow-Methods`, plus
`Vary: Origin, Access-Control-Request-Method, Access-Control-Request-Headers`. Routa never
sets `Access-Control-Allow-Origin`, so cross-origin access still requires an explicit CORS
policy in your application.

## Input Parsing Details

| Source    | Behavior                                                                                             |
| --------- | ---------------------------------------------------------------------------------------------------- |
| `params`  | Values from dynamic path segments                                                                    |
| `query`   | The query string as a flat record; repeated keys collapse to the last value                          |
| `headers` | All request headers, lowercased                                                                      |
| `cookies` | Parsed from the `Cookie` header and URI-decoded, falling back to the raw value on malformed encoding |
| `body`    | Requires `application/json` or a `+json` media type, otherwise `415`                                 |

## Response Serialization

Handlers and middleware rejects return `{ type, data }`, or just `{ type }` for an outcome
without a `schema`. An outcome that declares `headers` or `cookies` also returns them. Routa
always looks up the type and status from the matching response definition. It requires `data` for an outcome with a `schema` and rejects `data` on one
without, so an outcome without a schema sends an empty body whatever its status. With the
default `responseValidation: "development"`, Routa parses `data` through the response schema
in `routa dev`, compares the parsed value with the value the handler returned, and skips
both in `routa start`. Set `responseValidation: "always"` to do both in both modes. The CLI
passes the mode explicitly; Routa does not infer it from `NODE_ENV`.

Routa sends the value the handler returned, never the parsed value. Data that does not match
the schema, or that the schema would change, produces a handler-output problem. Data that
cannot be serialized as JSON also produces a handler-output problem rather than a partial
response. When serializing throws, for a bigint, a circular reference, or a `toJSON()` method or
getter in the data, it is an unexpected failure whose thrown value goes to `onRequestError`;
data JSON writes no text for, such as `undefined`, is a contract violation. See [Configuration](/docs/reference/configuration/) for the policy table.

An outcome's declared `headers` are part of the same step. In every mode Routa checks that
the result writes only declared names, writes each once whatever its case, includes every
required header, and uses safe values: strings without line breaks or surrounding
whitespace, finite numbers, and booleans. It serializes values to strings in declaration
order. A violation, or a header that a lifecycle header also claims, is a handler-output
problem, and Routa never overwrites a header. Parsing header values and comparing the result
follow `responseValidation` exactly like `data`.

Return the declared result object from handlers and middleware. A raw `Response` is not a
response escape hatch: returning one is invalid handler output, while throwing one is
handled as an internal error. Both produce a generic `500` problem response.

## Logging

When a logger is configured, `createHonoApp` records `http.response.prepared` at `info` once
for every response it prepares, with `requestId`, `method`, `route`, `status`, and
`durationMs`. It records `http.error` at `error` when a Routa route fails unexpectedly and Routa
answers with a 500 or above, with `requestId`, `method`, `route`, `status`, and the failure's
`code` and `stage`. A declared
outcome with a 5xx status, such as a `503` your handler returns, is an application decision and
logs only `http.response.prepared`. The
[events table](/docs/reference/configuration/#events-routa-writes) defines each field. Response
and middleware context schema failures also include `issueCount` and the distinct, sorted
`issueCodes`; issue paths and rejected values are never logged.

```txt
{"timestamp":"2026-01-01T00:00:00.000Z","level":"error","event":"http.error","message":"Request failed.","data":{"requestId":"5e8f2a1c-3b4d-4c6e-9f0a-1b2c3d4e5f6a","method":"GET","route":"/orders/:id","status":500,"code":"unexpected_failure","stage":"handler"}}
```

To see the error itself, configure
[`onRequestError`](/docs/reference/configuration/#onrequesterror). It receives the original
error and the same metadata for each failure `http.error` records, even with `logger: false`,
and never changes the response. A `ZodError` that escapes a handler or `createContext`, and a
request body that cannot be read or parsed, including a body stream that errors when the client
aborts, answer `400` and are not reported.

Request events never carry the request's path, query, body, raw headers, cookies, credentials,
principal, or any error's message, name, or stack. A thrown authenticator, an invalid principal,
and a failed services factory all log the same `http.error` fields, so a provider error that
includes a credential never reaches the logs.

Every event passes through the logger's
[sanitization](/docs/reference/core/#sanitization) before its sink receives it. A sink that
throws or rejects, or an event that cannot be sanitized, never changes the response.

Handlers always receive `ctx.logger`. With logging disabled it is a complete no-op
implementation of the same type.

<Aside type="caution" title="v0 status">
	JSON is the only supported content type at the request and response boundary. Streaming
	responses, file uploads, and content negotiation beyond JSON are deferred.
</Aside>
