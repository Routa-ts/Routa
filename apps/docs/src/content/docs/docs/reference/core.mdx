## `createRouta`

```ts
function createRouta<const TConfig extends RoutaConfig>(
	config: TConfig & AuthenticationChecks<NoInfer<TConfig>>,
): TConfig & RoutaConfig
```

Preserves an application configuration object with Routa's typing. Export the result as
the default export of `src/routa.ts`, which the runtime imports at boot.

| Option               | Type                         | Default                 |
| -------------------- | ---------------------------- | ----------------------- |
| `host`               | `string`                     | `"127.0.0.1"`           |
| `port`               | `number`                     | `3000`                  |
| `logger`             | `RoutaLogger \| false`       | Built-in console logger |
| `lifecycleHeaders`   | `boolean`                    | `false`                 |
| `responseValidation` | `"development" \| "always"`  | `"development"`         |
| `services`           | `ApplicationServicesFactory` | None                    |
| `authentication`     | `AuthenticationConfig`       | None                    |

`AuthenticationChecks` fails a scheme whose authenticator returns a principal the principal
schema does not accept as input, a rejection with fields besides `type`, or a `priority` entry
that names no configured scheme.

```ts title="src/routa.ts"
import { createRouta } from "@routa-ts/core";

export default createRouta({
	host: "127.0.0.1",
	port: 3000,
	lifecycleHeaders: true,
	responseValidation: "always",
});
```

See [Configuration](/docs/reference/configuration/) for environment precedence.

## `defineServices`

```ts
function defineServices<TServices>(): ServicesHelper<TServices>

type ServicesHelper<TServices> = <TContext = ApplicationServicesContext>(
	factory: (context: TContext) => TServices | Promise<TServices>,
) => (context: TContext) => TServices | Promise<TServices>
```

Fixes a service contract and returns a helper that checks a factory against it and returns
the factory unchanged. `TServices` must name each service as a required property; optional
services and index signatures are type errors. Where you place the helper's result types
the factory's argument: `createRouta({ services })` passes an `ApplicationServicesContext`,
and a route root's or `createRoute`'s `services` passes a `RequestServicesContext`.

| Factory argument | Type          | Purpose                                                                   |
| ---------------- | ------------- | ------------------------------------------------------------------------- |
| `logger`         | `RoutaLogger` | Application factories: the configured logger, or a no-op logger           |
| `ctx`            | `object`      | Request factories: earlier middleware context, earlier services, `logger` |
| `onCleanup`      | `OnCleanup`   | Registers a callback that releases a resource the factory owns            |

The factory may be sync or async and returns exactly the contract's services.

```ts title="src/services.ts"
import { defineServices } from "@routa-ts/core";

export interface AppServices {
	clock: { now(): Date };
}

export const defineAppServices = defineServices<AppServices>();
export const appServices = defineAppServices(() => ({ clock: { now: () => new Date() } }));
```

`routa check` reports `ROUTA_SERVICES_UNRESOLVED`, `ROUTA_SERVICES_CONTRACT_UNRESOLVED`, or
`ROUTA_SERVICES_CONTRACT_UNSUPPORTED` for a declaration it cannot read. See
[Services](/docs/concepts/services/).

## `createRoute`

```ts
function createRoute<TInput, TResponses, TMiddleware>(
	contract: RouteContract<TInput, TResponses, TCtx, TMiddleware>,
): RouteContract<TInput, TResponses, TCtx, TMiddleware>
```

Declares one HTTP method. The function returns its argument unchanged; its purpose is to
capture literal types so `run` receives typed `input`, `ctx`, and `response` and is constrained to the
declared outcomes.

| Field         | Type                                                                                | Required |
| ------------- | ----------------------------------------------------------------------------------- | -------- |
| `input`       | `{ params?, query?, headers?, cookies?, body? }` of Zod schemas                     | No       |
| `responses`   | `Record<string, { status; description?; schema?; headers?; cookies? }>`             | Yes      |
| `middleware`  | `readonly MiddlewareContract[]`                                                     | No       |
| `services`    | A `defineServices` helper result, run once per request to this method               | No       |
| `deprecation` | `{ sunset?: string; replacement?: string }`                                         | No       |
| `run`         | `({ input, ctx, response }) => { type, data, headers, cookies }` or a promise of it | Yes      |

`deprecation.replacement` accepts a registered route path beginning with `/` or an
absolute `http:`/`https:` URL. Local paths are checked against the generated route
registry.

An outcome with a `schema` returns `data` typed from the schema. An outcome without one is
intentionally bodyless: it returns only `type` and sends an empty body. `description` is
optional text for the OpenAPI response; without it, Routa uses the outcome name, so
`notFound` becomes "Not found".

An outcome's `headers` is a Zod object keyed by lowercase header names, with string,
number, or boolean values. The result's `headers` field is required when any declared header
is required, optional when all are, and forbidden when the outcome declares none. Routa owns
`content-type`, `content-length`, `transfer-encoding`, `connection`, and `set-cookie`, and
with `lifecycleHeaders` on it owns `deprecation`, `sunset`, and the successor `link`. See
[Schemas](/docs/concepts/schemas/#response-headers).

An outcome's `cookies` lists the `createCookie` handles it may emit. A bare handle is optional;
`{ handle, required: true }` requires a `set` or `clear` effect for it. The result's `cookies`
field is an array of `set` and `clear` effects for those handles, and it is forbidden when the
outcome declares none. See [`createCookie`](#createcookie).

**Errors:** returning an undeclared `type` is a compile error and, at runtime, an
`Invalid handler output` problem response. Result objects may contain only `type`, `data`,
`headers`, and `cookies`. `data` is required for an outcome with a `schema` and forbidden for one without.
TypeScript also rejects a `schema` on a `204`, `205`, or `304` outcome and on any `HEAD`
outcome, an informational `1xx` status, a `304` outside `GET` and `HEAD`, and response
schemas that change values. A hand-built contract that breaks the status and method rules
fails when the app registers it. A response schema that changes values is caught by
`routa check`, or at request time when response validation is on and the schema changes
the returned value.

```ts
import { createRoute } from "@routa-ts/core";
import { z } from "zod";

export const getStatus = createRoute({
	responses: {
		success: { status: 200, schema: z.object({ ok: z.boolean() }) },
	},
	run: ({ response }) => response.success({ ok: true }),
});
```

## `ResponseBuilders`

```ts
type ResponseBuilders<TResponses extends RouteResponses> = {
	readonly [K in Exclude<keyof TResponses & string, OutcomesWithRequiredCookies<TResponses>>]:
		TResponses[K] extends { readonly schema: infer TSchema extends ZodType }
			? (
					data: SchemaOutput<TSchema>,
					...headers: BuilderHeaderArgs<TResponses[K]>
				) => Extract<OutcomeResult<K, TResponses[K]>, { readonly data: unknown }>
			: (...headers: BuilderHeaderArgs<TResponses[K]>) => OutcomeResult<K, TResponses[K]>
}

// Internal helpers, not exported
type BuilderHeaderArgs<TOutcome> = TOutcome extends { readonly headers: infer THeaders extends ZodType }
	? {} extends SchemaOutput<THeaders>
		? [headers?: SchemaOutput<THeaders>] // every declared header is optional
		: [headers: SchemaOutput<THeaders>]
	: [] // no headers declared

type OutcomesWithRequiredCookies<TResponses extends RouteResponses> = {
	[K in keyof TResponses & string]: TResponses[K] extends {
		readonly cookies: readonly (infer TEntry)[]
	}
		? Extract<TEntry, { readonly required: true }> extends never
			? never
			: K
		: never
}[keyof TResponses & string]
```

An outcome that lists a required cookie has no builder. Return its result object instead, so
you can set the cookie effect.

```ts
import { createRoute } from "@routa-ts/core";
import { z } from "zod";

export const getItem = createRoute({
	responses: {
		ok: {
			status: 200,
			schema: z.object({ id: z.string() }),
			headers: z.object({ etag: z.string(), "x-cached": z.boolean().optional() }),
		},
		notModified: { status: 304, headers: z.object({ etag: z.string() }) },
	},
	run: ({ response }) => {
		const etag = '"v1"';
		// A body outcome takes its data, then its headers.
		return response.ok({ id: "1" }, { etag });
		// A bodyless outcome takes only its headers: response.notModified({ etag })
	},
});
```

A body outcome's builder takes the data, then a `headers` argument when the outcome declares
headers. A bodyless outcome's builder takes only `headers`. The argument is required when any
declared header is required, optional when all are, and absent when the outcome declares none.

Handlers receive `response: ResponseBuilders<TResponses>`. Each method uses the name
and schema of one outcome in the route's own `responses` declaration. There are no
built-in outcome names, and middleware rejects do not add builder methods.

| Parameter | Type                                   | Purpose                                         |
| --------- | -------------------------------------- | ----------------------------------------------- |
| `data`    | Selected outcome schema's output type  | Body data for the result                        |
| `headers` | Selected outcome `headers` output type | Response headers, when the outcome declares any |

An outcome without a `schema` has a builder with no data parameter, such as
`response.noContent()`. An outcome that declares a required cookie has no builder; return
its result object so you can set the cookie effect. A builder returns `{ type, data, headers }`, or `{ type, headers }`
for an outcome without a schema (`headers` appears only when you pass it), without sending a response. Return that result from
`run` to select the outcome. Routa applies the declared status, configured response
validation, and JSON serialization. Existing object returns remain supported.

```ts
import { createRoute } from "@routa-ts/core";
import { z } from "zod";

export const getGreeting = createRoute({
	responses: {
		ok: { status: 200, schema: z.object({ message: z.string() }) },
	},
	run: ({ response }) => response.ok({ message: "Hello!" }),
});
```

**Errors:** TypeScript rejects undeclared methods and data that does not match the
selected schema. Runtime payload validation follows the `responseValidation` setting.
The `response` object is frozen; its methods cannot be replaced.

`RouteHandlerArgs<TInput, TCtx, TResponses = RouteResponses>` accepts the response
contract as its third type parameter when you explicitly annotate handler arguments.

## `createRouteRoot`

```ts
function createRouteRoot<const TPath extends RegisteredRoutePath>(
	path: TPath,
): <const TConfig extends RouteRootConfigForCtx<Register["routeCtxByPath"][TPath]>>(
	config: TConfig,
) => TConfig
```

Binds a file to a URL path and returns the helper used as the file's default export. The
returned helper accepts `get`, `post`, `put`, `patch`, `delete`, `head`, `middleware`, and
`services`, and rejects every other key. `options` is never accepted. `services` takes a
`defineServices` helper result that runs once per request to any of the file's methods; see
[route-file and method services](/docs/concepts/services/#route-file-and-method-services).

```ts title="src/routes/users/$userId/route.ts"
import { createRoute, createRouteRoot } from "@routa-ts/core";
import { z } from "zod";
import { withAudit } from "../../../middleware/audit.js";

const route = createRouteRoot("/users/:userId");

export default route({
	middleware: [withAudit],
	get: createRoute({
		responses: {
			success: {
				status: 200,
				schema: z.object({ id: z.string() }),
			},
		},
		run: () => ({ type: "success", data: { id: "usr_1" } }),
	}),
});
```

The path must use `:name` for dynamic segments even though the filesystem uses `$name`.
Context types come from the `Register` augmentation in `.routa/routes.gen.ts`, so a path
missing from generated metadata produces a type error.

## `createRouteRootFactory`

```ts
function createRouteRootFactory<
	TCtxByPath extends Record<string, Partial<Record<HttpMethod, unknown>>>,
>(): <TPath extends keyof TCtxByPath & string>(
	path: TPath,
) => <const TConfig extends RouteRootConfigForCtx<TCtxByPath[TPath]>>(
	config: TConfig,
) => TConfig
```

Returns a `createRouteRoot` bound to an explicit context map instead of the generated
`Register` augmentation. Use it in tests, libraries, or tooling that must work without a
generated project. Prefer `createRouteRoot` in application code.

```ts
import { createRoute, createRouteRootFactory } from "@routa-ts/core";
import { z } from "zod";

type TestContextByPath = {
	"/health": { get: Record<never, never> };
};

const createTestRouteRoot = createRouteRootFactory<TestContextByPath>();
const route = createTestRouteRoot("/health");

export default route({
	get: createRoute({
		responses: {
			success: { status: 200, schema: z.object({ ok: z.boolean() }) },
		},
		run: () => ({ type: "success", data: { ok: true } }),
	}),
});
```

## `createMiddleware`

```ts
function createMiddleware<TRequires, TProvides, TRejects, TInput>(
	contract: MiddlewareContract<TRequires, TProvides, TRejects, TInput>,
): MiddlewareContract<TRequires, TProvides, TRejects, TInput>

function createMiddleware<Requirements>(): MiddlewareHelper<Requirements>

type MiddlewareHelper<TServices extends object> = <
	const TRequires extends readonly RegisteredCtxKey[] = readonly RegisteredCtxKey[],
	const TProvides extends MiddlewareProvidesSpec = Record<never, never>,
	const TRejects extends MiddlewareRejectsSpec = Record<never, never>,
	const TInput extends RouteInput | undefined = undefined,
	const TNames extends readonly (keyof TServices & string)[] = readonly (keyof TServices & string)[],
>(
	contract: MiddlewareContract<TRequires, TProvides, TRejects, TInput, TServices> & {
		readonly requiresServices: TNames & RequirementListChecks<TServices, NoInfer<TNames>>
		readonly rejects?: ResponseChecks<NoInfer<TRejects>>
		readonly provides?: ReservedContextChecks<NoInfer<TProvides>>
	},
) => MiddlewareContract<TRequires, TProvides, TRejects, TInput, TServices>
```

`RequirementListChecks` fails a `requiresServices` list that is not a literal list, leaves out
a name the requirement interface declares, or repeats one. `ResponseChecks` and
`ReservedContextChecks` apply the same rules as the contract form.

| Field              | Type                                                                    | Purpose                                        |
| ------------------ | ----------------------------------------------------------------------- | ---------------------------------------------- |
| `requires`         | `readonly string[]`                                                     | Context keys that must already exist           |
| `requiresServices` | `readonly (keyof Requirements)[]`                                       | Helper form only: every requirement name, once |
| `provides`         | `Record<string, ZodType>`                                               | Context keys this middleware adds              |
| `rejects`          | `Record<string, { status; description?; schema?; headers?; cookies? }>` | Early responses it can return                  |
| `input`            | Same shape as a route `input`                                           | Request data the middleware needs              |
| `openapi`          | `{ security?, permissions? }`                                           | Metadata emitted into generated OpenAPI        |
| `run`              | `({ input, ctx, next }) => …`                                           | The implementation                             |

`run` either returns one of its own reject outcomes or returns `next(providedCtx)`. `next()`
resolves to an opaque `MiddlewareContinuation`, the outcome the rest of the chain selected;
return it unchanged. Routa parses every
declared `provides` value before merging any of them into `ctx`, and downstream code
receives the parsed output. Undeclared top-level keys are omitted. A normal `z.object()`
schema strips unknown nested keys; use `.strict()` on that schema when unknown nested keys
must reject the request instead.

**Errors:** `next()` called more than once throws. A `provides` value that fails its
schema, or a value other than `next()`'s result returned after calling it, produces an
`Invalid handler output` response. Reject statuses must be 4xx or 5xx.

Called with only a type argument, `createMiddleware<Requirements>()` returns a
`MiddlewareHelper`. The helper takes the same contract plus `requiresServices`, which must list
each of the interface's names exactly once, and types the callback's `ctx.services` as
`Readonly<Requirements>`. `Requirements` follows the service contract rules: required, plainly
named members and no index signature. The direct form has no typed `ctx.services` and rejects
`requiresServices`. A middleware whose required service is missing from its stage's
`ctx.services` at request time fails with the standard `500` problem before its callback runs;
see [Middleware Service Requirements](/docs/concepts/services/#middleware-service-requirements).

```ts
import { randomUUID } from "node:crypto";
import { createMiddleware } from "@routa-ts/core";
import { z } from "zod";

export const withRequestId = createMiddleware({
	provides: { requestId: z.string().uuid() },
	run: ({ next }) => next({ requestId: randomUUID() }),
});
```

```ts
import { createMiddleware } from "@routa-ts/core";

export interface ClockRequirements {
	clock: { now(): Date };
}

const defineClockMiddleware = createMiddleware<ClockRequirements>();

export const withClock = defineClockMiddleware({
	requiresServices: ["clock"],
	run: ({ ctx, next }) => {
		ctx.services.clock.now();
		return next();
	},
});
```

## `bearer`

```ts
function bearer<const TResult extends AuthenticationResult>(options: {
	challenge?: { realm?: string };
	authenticate: (
		credential: string,
		context: AuthenticatorContext,
	) => TResult | Promise<TResult>;
}): BearerScheme<TResult>

type AuthenticationResult<TPrincipal = unknown> =
	| { readonly type: "authenticated"; readonly principal: TPrincipal }
	| { readonly type: "rejected" }
```

Declares a credential scheme that reads `Authorization: Bearer <token>`. Place it in
`authentication.schemes` in `createRouta`, keyed by the scheme name. Routa extracts the token,
calls `authenticate` once per request that presents one, and parses an authenticated
principal with the principal schema.

| Option         | Type                                            | Purpose                                                             |
| -------------- | ----------------------------------------------- | ------------------------------------------------------------------- |
| `challenge`    | `{ realm?: string }`                            | Static challenge override; a literal read by `routa check`          |
| `authenticate` | `(credential, context) => AuthenticationResult` | Your verification code: return a principal candidate or a rejection |

`context` holds `logger` and, when `src/routa.ts` declares them, the application `services`.
It has no route-file or method services and no request. Return `{ type: "rejected" }` for a
credential that is not valid. Throw only for unexpected failures, which stay `500` responses.
`realm` must be printable ASCII without `"` or `\`.

```ts title="src/routa.ts"
import { bearer, createRouta } from "@routa-ts/core";
import { z } from "zod";

export default createRouta({
	authentication: {
		principal: z.object({ type: z.literal("service"), id: z.string() }),
		schemes: {
			serviceToken: bearer({
				challenge: { realm: "internal" },
				authenticate: (token) =>
					token === process.env.SERVICE_TOKEN
						? { type: "authenticated", principal: { type: "service", id: "billing" } }
						: { type: "rejected" },
			}),
		},
	},
});
```

**Errors:** throws a `TypeError` when `authenticate` is not a function, or when `challenge`
declares a key other than `realm` or an invalid realm.

## `apiKey`

```ts
function apiKey<const TResult extends AuthenticationResult>(options: {
	header: string;
	challenge?: { realm?: string };
	authenticate: (
		credential: string,
		context: AuthenticatorContext,
	) => TResult | Promise<TResult>;
}): ApiKeyScheme<TResult>
```

Declares a credential scheme that reads an API key from one request header. Routa passes the
header's value to `authenticate` once per request that selects it, and parses an
authenticated principal with the principal schema. `authenticate`, `context`, and the result
follow the same contract as [`bearer`](#bearer).

| Option         | Type                                            | Purpose                                                             |
| -------------- | ----------------------------------------------- | ------------------------------------------------------------------- |
| `header`       | `string`                                        | The header that carries the key, such as `"x-api-key"`; a literal   |
| `challenge`    | `{ realm?: string }`                            | Static challenge override; a literal read by `routa check`          |
| `authenticate` | `(credential, context) => AuthenticationResult` | Your verification code: return a principal candidate or a rejection |

The header name is an RFC 9110 token, compared ignoring case. It cannot be `Authorization` or
`Cookie`, which Bearer and session schemes read. A missing credential challenges `ApiKey`, or
`ApiKey realm="…"` with the override; a failed one challenges the same, with no error details.
OpenAPI declares the scheme as `{ type: "apiKey", in: "header", name }`.

```ts title="src/routa.ts"
import { apiKey, createRouta } from "@routa-ts/core";
import { z } from "zod";
import { findServiceKey } from "./service-keys.js";

export default createRouta({
	authentication: {
		principal: z.object({ type: z.literal("service"), id: z.string() }),
		schemes: {
			serviceKey: apiKey({
				header: "x-api-key",
				authenticate: async (key) => {
					const service = await findServiceKey(key);
					return service
						? { type: "authenticated", principal: { type: "service", id: service.id } }
						: { type: "rejected" };
				},
			}),
		},
	},
});
```

**Errors:** throws a `TypeError` when `header` is not a header name, `authenticate` is not a
function, or `challenge` declares a key other than `realm` or an invalid realm.

## `sessionCookie`

```ts
function sessionCookie<const TResult extends AuthenticationResult>(options: {
	cookie: string;
	challenge?: { realm?: string };
	authenticate: (
		credential: string,
		context: AuthenticatorContext,
	) => TResult | Promise<TResult>;
}): SessionCookieScheme<TResult>
```

Declares a credential scheme that reads a session from one request cookie. Routa passes the
cookie's percent-decoded value to `authenticate` once per request that selects it, and parses
an authenticated principal with the principal schema. Your application owns sessions: how it
creates, stores, signs, and expires them. `authenticate`, `context`, and the result follow the
same contract as [`bearer`](#bearer).

| Option         | Type                                            | Purpose                                                             |
| -------------- | ----------------------------------------------- | ------------------------------------------------------------------- |
| `cookie`       | `string`                                        | The cookie that carries the session, such as `"session"`; a literal |
| `challenge`    | `{ realm?: string }`                            | Static challenge override; a literal read by `routa check`          |
| `authenticate` | `(credential, context) => AuthenticationResult` | Your verification code: return a principal candidate or a rejection |

The cookie name is an RFC 6265 token, compared exactly. A missing credential challenges
`Session`, or `Session realm="…"` with the override; a failed one challenges the same, with no
error details. OpenAPI declares the scheme as `{ type: "apiKey", in: "cookie", name }`.

```ts title="src/routa.ts"
import { createRouta, sessionCookie } from "@routa-ts/core";
import { z } from "zod";
import { findSession } from "./sessions.js";

export default createRouta({
	authentication: {
		principal: z.object({ type: z.literal("user"), id: z.string() }),
		schemes: {
			session: sessionCookie({
				cookie: "session",
				authenticate: async (value) => {
					const session = await findSession(value);
					return session
						? { type: "authenticated", principal: { type: "user", id: session.userId } }
						: { type: "rejected" };
				},
			}),
		},
	},
});
```

**Errors:** throws a `TypeError` when `cookie` is not a cookie name, `authenticate` is not a
function, or `challenge` declares a key other than `realm` or an invalid realm.

## `requireAuth`

```ts
function requireAuth(options?: { schemes: readonly SchemeName[] }): RequireAuthMiddleware
```

A middleware guard that returns `authenticationRequired` (`401`) for an anonymous request and
lets an authenticated one continue. The handler sees `ctx.auth` narrowed to
`{ status: "authenticated", scheme, principal }`. Middleware placed after the guard receives an
authenticated value at runtime, but a middleware contract that declares `requires: ["auth"]`
is typed with the anonymous-or-authenticated union, so check `ctx.auth.status` before reading
`principal`. Omit `options` to accept any
configured scheme, or list the accepted schemes inline; `SchemeName` is the union of names
`routa generate` read from `src/routa.ts`.

Write the call inline in a route root's or a `createRoute`'s `middleware`, so `routa check`
can read it. It requires [`authentication`](/docs/reference/configuration/#authentication) in
`createRouta`.

```ts title="src/routes/projects/route.ts"
import { createRoute, createRouteRoot, requireAuth } from "@routa-ts/core";
import { z } from "zod";

export default createRouteRoot("/projects")({
	post: createRoute({
		middleware: [requireAuth()],
		input: { body: z.object({ name: z.string() }) },
		responses: { created: { status: 201, schema: z.object({ owner: z.string() }) } },
		run: ({ ctx }) => ({ type: "created", data: { owner: ctx.auth.principal.id } }),
	}),
});
```

Listing `schemes` restricts which credentials can authenticate the operation, not only who
passes the guard. Routa selects only among credentials of the schemes every `requireAuth` on
the operation allows, so `requireAuth({ schemes: ["session"] })` with a route-level
`requireAuth({ schemes: ["session", "userToken"] })` accepts sessions alone, and a valid
Bearer token there fails with `authenticationFailed`. See
[Credential selection](/docs/reference/runtime-behavior/#credential-selection).

The guard owns the `authenticationRequired` outcome, so a route outcome with that name is a
type error. Its `401` carries a `WWW-Authenticate` challenge for every accepted scheme, in
priority order; see
[Runtime behavior](/docs/reference/runtime-behavior/#outcomes-and-challenges).

**Errors:** throws a `TypeError` for an empty `schemes` list. `routa check` reports
`ROUTA_AUTH_NOT_CONFIGURED`, `ROUTA_AUTH_SCHEME_UNKNOWN`, `ROUTA_AUTH_REQUIREMENT_EMPTY` for an
empty list or guards on one operation that allow no scheme in common,
`ROUTA_AUTH_REQUIREMENT_UNRESOLVED`, and, for a guard a folder `middleware.ts` exports,
`ROUTA_AUTH_REQUIREMENT_UNSUPPORTED`. Registration throws when authentication is not
configured, a guard names an undeclared scheme, or the guards allow no scheme in common.

<Aside type="caution" title="Inline guards only">
	`requireAuth` works inline at route and method level. A folder `middleware.ts` cannot
	export it yet.
</Aside>

## `AuthContext`

```ts
type AuthContext<TScheme extends string = string, TPrincipal = Principal> =
	| AnonymousAuthContext
	| AuthenticatedAuthContext<TScheme, TPrincipal>

type AnonymousAuthContext = { readonly status: "anonymous" }

type AuthenticatedAuthContext<TScheme extends string = string, TPrincipal = Principal> = {
	readonly status: "authenticated"
	readonly scheme: TScheme
	readonly principal: TPrincipal
}
```

The type of `ctx.auth`. Routa provides it only when `src/routa.ts` configures authentication;
otherwise `ctx.auth` exists only when application middleware provides it, with that
middleware's type. `.routa/routes.gen.ts` types it for each
operation: an operation without `requireAuth` gets `AuthContext`, and an operation behind
`requireAuth` gets `AuthenticatedAuthContext`. `TPrincipal` is the principal schema's output.
Middleware reads `ctx.auth` by declaring `requires: ["auth"]` and sees `AuthContext`.

```ts title="src/routes/me/route.ts"
import { createRoute, createRouteRoot } from "@routa-ts/core";
import { z } from "zod";

export default createRouteRoot("/me")({
	get: createRoute({
		responses: { ok: { status: 200, schema: z.object({ id: z.string().nullable() }) } },
		run: ({ ctx }) => ({
			type: "ok",
			data: { id: ctx.auth.status === "authenticated" ? ctx.auth.principal.id : null },
		}),
	}),
});
```

## `createCookie`

```ts
function createCookie<const TConfig extends CookieConfig>(
	config: TConfig, // also constrained by the cookie rules TypeScript can check
): CookieHandle<TConfig>
```

| Field         | Type                           | Required | Purpose                                              |
| ------------- | ------------------------------ | -------- | ---------------------------------------------------- |
| `name`        | `string`                       | Yes      | RFC 6265 token                                       |
| `schema`      | Zod string, number, or boolean | Yes      | Validates the value; must not change it              |
| `httpOnly`    | `boolean`                      | Yes      | Adds `HttpOnly`                                      |
| `secure`      | `boolean`                      | Yes      | Adds `Secure`                                        |
| `sameSite`    | `"strict" \| "lax" \| "none"`  | Yes      | Sets `SameSite`; `"none"` requires `secure: true`    |
| `path`        | `string`                       | Yes      | Starts with `/`; printable ASCII, no trailing space  |
| `domain`      | `string`                       | No       | Host name, with or without a leading dot             |
| `maxAge`      | `number`                       | No       | Non-negative whole seconds                           |
| `expires`     | `string`                       | No       | ISO 8601 date-time, such as `"2030-01-01T00:00:00Z"` |
| `partitioned` | `boolean`                      | No       | Adds `Partitioned`; requires `secure: true`          |

```ts
type CookieSameSite = "strict" | "lax" | "none"

type CookieHandle<TConfig extends CookieConfig> = Readonly<TConfig> & {
	set(value: SchemaOutput<TConfig["schema"]>): CookieEffect<CookieHandle<TConfig>>
	clear(): CookieEffect<CookieHandle<TConfig>>
}

type CookieEffect<THandle = AnyCookie> = {
	readonly kind: "set" | "clear"
	readonly cookie: THandle
	readonly value?: unknown
}

type AnyCookie = Readonly<CookieConfig> & {
	set(value: never): CookieEffect<any>
	clear(): CookieEffect<any>
}

type RequiredCookie<THandle extends AnyCookie = AnyCookie> = {
	readonly handle: THandle
	readonly required: true
}
```

`CookieConfig` is the field table above. `AnyCookie` accepts any handle, and a
`RequiredCookie` entry in an outcome's `cookies` makes the outcome return an effect for that
handle.

The handle exposes `set(value)` and `clear()`. Both are pure: they return a `CookieEffect`
bound to the handle, and Routa turns the effects an outcome returns into repeated
`Set-Cookie` fields. List the handle in an outcome's `cookies` for the outcome to return its
effects. `routa check` and OpenAPI read the name and attributes from source, so write them
as literals.

**Errors:** TypeScript rejects missing required attributes, a value schema that is not scalar
or that changes values, `SameSite=None` or `Partitioned` without `secure: true`, and the
`__Secure-` and `__Host-` prefix rules. `routa check` (`ROUTA_RESPONSE_COOKIE_*`) and
`createCookie` itself, which throws, also reject an invalid name, path, domain, `maxAge`, or
`expires`. Returning an effect for a handle the outcome does not list, the same identity
twice, or a value that cannot be encoded safely produces an `Invalid handler output`
response. See [Schemas](/docs/concepts/schemas/#response-cookies) for the rules, encoding, and
clearing.

```ts
import { createCookie } from "@routa-ts/core";
import { z } from "zod";

export const theme = createCookie({
	name: "theme",
	schema: z.enum(["light", "dark"]),
	httpOnly: false,
	secure: true,
	sameSite: "lax",
	path: "/",
});

theme.set("dark"); // a set effect
theme.clear(); // a clear effect
```

## `createHonoApp`

```ts
function createHonoApp(routes: readonly HonoRoute[], options?: CreateHonoAppOptions): Hono
```

Builds the Hono application from route definitions. It provides no application services:
routes that read them need [`createApplication`](#createapplication) with a services
factory. Call it directly in tests of routes that use no application services.

| Parameter                    | Type                        | Purpose                                             |
| ---------------------------- | --------------------------- | --------------------------------------------------- |
| `routes[].method`            | `HttpMethod`                | Lowercase method name                               |
| `routes[].path`              | `string`                    | Hono path with `:name` parameters                   |
| `routes[].contract`          | `AnyRouteContract`          | The `createRoute` result                            |
| `routes[].createContext`     | `() => object`              | Optional base context, must return a plain object   |
| `routes[].services`          | `RouteServices`             | Optional `routeFile` and `method` request services  |
| `routes[].middlewareNames`   | `readonly string[]`         | Names each middleware of the chain in messages      |
| `options.logger`             | `RoutaLogger`               | Enables `http.request` and `http.error` logging     |
| `options.lifecycleHeaders`   | `boolean`                   | Emit `Deprecation`, `Sunset`, and `Link`            |
| `options.responseValidation` | `"development" \| "always"` | Response schema policy; defaults to `"development"` |
| `options.runtimeMode`        | `"dev" \| "start"`          | Explicit mode; defaults to `"dev"` for direct use   |
| `options.authentication`     | `AuthenticationConfig`      | Resolves `ctx.auth` and enforces `requireAuth`      |

Registration throws for an explicitly declared `options` method, a duplicate
method-and-path pair, a `GET` or `HEAD` contract declaring a body, and duplicate reject
keys within one chain. With `authentication`, it also throws for an invalid configuration,
a route outcome named `authenticationFailed`, one named `authenticationRequired` behind a
`requireAuth` guard, a route outcome named `ambiguousCredentials` where strict mode can return
it, and middleware that provides `auth`. Without it, a `requireAuth` guard throws.

```ts
type RouteServices = {
	readonly routeFile?: RequestServicesDeclaration
	readonly method?: RequestServicesDeclaration
}

type RequestServicesDeclaration = {
	readonly factory: RequestServicesFactory
	readonly names: readonly string[]
	readonly after: number
}
```

Each `RouteServices` entry pairs a request factory with its contract's `names` and `after`,
the number of middleware at the start of the route's chain that run before the factory.
Registration also throws when `after` falls outside the chain, when method services run
before route-file services, when the application, route-file, and method services share a
name, or when the contract declares `services` that `routes[].services.method` does not
supply.

`middlewareNames` lists a name for each entry of `contract.middleware`, in order. The CLI
runtime passes the export names `routa generate` read. A middleware without a name appears in
messages as `middleware[i]`.

```ts
import { createHonoApp } from "@routa-ts/core/hono";
import route from "./routes/users/route.js";

const app = createHonoApp([{ method: "post", path: "/users", contract: route.post }]);
```

## `createApplication`

```ts
function createApplication(
	routes: readonly HonoRoute[],
	options?: CreateApplicationOptions,
): Promise<RoutaApplication>
```

Creates one application instance. It runs the services factory once, checks the returned
names, and registers the routes with the services exposed as `ctx.services`. `routa dev` and
`routa start` call it for you.

| Option             | Type                         | Purpose                                                          |
| ------------------ | ---------------------------- | ---------------------------------------------------------------- |
| `services.factory` | `ApplicationServicesFactory` | The factory from `createRouta`                                   |
| `services.names`   | `readonly string[]`          | The contract's names, as generated in `routaApplicationServices` |
| Every other option | `CreateHonoAppOptions`       | Same as `createHonoApp`                                          |

The instance has two members:

| Member    | Type                                      | Behavior                                                                                                                                                          |
| --------- | ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fetch`   | `(request: Request) => Promise<Response>` | Handles one request. Rejects once disposal has started                                                                                                            |
| `dispose` | `() => Promise<void>`                     | Stops accepting requests, waits for accepted ones, then runs cleanup once. Repeated calls share one outcome; rejects with an `AggregateError` when cleanup failed |

`dispose` sets no deadline: a request or callback that never settles keeps it pending.

```ts
import { createApplication } from "@routa-ts/core/hono";
import route from "./routes/time/route.js";

const app = await createApplication([{ method: "get", path: "/time", contract: route.get }], {
	services: { names: ["clock"], factory: () => ({ clock: { now: () => new Date(0) } }) },
});

const response = await app.fetch(new Request("http://localhost/time"));
await app.dispose();
```

It rejects with the factory's error after running the factory's registered cleanup, with a
`TypeError` when the returned names differ from `services.names`, and with any
`createHonoApp` registration error after releasing the services.

## `createProjectApplication`

```ts
function createProjectApplication(
	load: ProjectModuleLoader,
	options: CreateProjectApplicationOptions,
```

Builds a project's application instance from its generated metadata without listening.
`routa dev`, `routa start`, and the generated `createTestApp` all build through it, so a

| Parameter              | Type                                 | Purpose                                                                                              |
| ---------------------- | ------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| `load`                 | `(file: string) => Promise<unknown>` | Imports a module by its path from the project root, such as `src/routa.ts` or `.routa/routes.gen.ts` |
| `options.runtimeMode`  | `"dev" \| "start"`                   | Explicit mode, as in `createHonoApp`                                                                 |
| `options.replacements` | `ServiceReplacements`                | Factories that replace whole scopes before construction, in the `createTestApp` options shape        |

It loads `.routa/routes.gen.ts`, each route file, its filesystem middleware, and
`src/routa.ts`, then calls `createApplication` with the configured logger, lifecycle

```ts
type ProjectApplication = {
	application: RoutaApplication
	config: RoutaConfig
	logger: RoutaLogger | undefined
	routes: readonly HonoRoute[]

```

`config` is the default export of `src/routa.ts`. `logger` is its configured logger, a

```ts
import { pathToFileURL } from "node:url";
import { createProjectApplication } from "@routa-ts/core/hono";

const { application } = await createProjectApplication(
```

`createApplication`.

## `isBodylessStatus`

```ts
function isBodylessStatus(status: number): boolean
```

Returns `true` for `204`, `205`, and `304`, the statuses HTTP forbids a body for. Routa
rejects a `schema` on outcomes with those statuses. It describes the status only: an outcome
without a `schema` is also bodyless at any other status.

```ts
import { isBodylessStatus } from "@routa-ts/core/hono";

export function responseFor(status: number, data: unknown): Response {
	const body = isBodylessStatus(status) ? null : JSON.stringify(data);
	return new Response(body, { status });
}
```

## `createLogger`

```ts
function createLogger(options?: CreateLoggerOptions): RoutaLogger
```

| Option    | Type                                                                       | Default            |
| --------- | -------------------------------------------------------------------------- | ------------------ |
| `enabled` | `boolean`                                                                  | `true`             |
| `level`   | `"trace" \| "debug" \| "info" \| "warn" \| "error" \| "fatal" \| "silent"` | `"info"`           |
| `sink`    | `(event: RoutaLogEvent) => void`                                           | Console writer     |
| `now`     | `() => Date`                                                               | `() => new Date()` |

The returned `RoutaLogger` is structural and depends on no logging package:

| Member                                             | Signature                                                 |
| -------------------------------------------------- | --------------------------------------------------------- |
| `trace`, `debug`, `info`, `warn`, `error`, `fatal` | `(event: string, message: string, data?: object) => void` |

| `bindings`                                         | `() => object`                                            |
| `isLevelEnabled`                                   | `(level) => boolean`                                      |

```ts title="src/routa.ts"
import { createRouta } from "@routa-ts/core";
import { createLogger } from "@routa-ts/core/logger";

});
```

Because the contract is structural, any object with these members works — an adapter over
Pino, Winston, or a hosted SDK needs no Routa-specific package.

## `OnCleanup`

```ts
type OnCleanup = (callback: () => unknown) => void
```

Registers a callback that releases a resource a services factory acquired. Routa awaits the
callbacks after the scope ends, one at a time, in reverse registration order, and attempts
every one even when an earlier one fails. A callback may return a promise.

| Parameter  | Type            | Purpose                        |
| ---------- | --------------- | ------------------------------ |
| `callback` | `() => unknown` | Releases one acquired resource |

Returns nothing.

```ts
import type { OnCleanup } from "@routa-ts/core";

export function startHeartbeat(onCleanup: OnCleanup): void {
	const timer = setInterval(() => {}, 30_000);
	onCleanup(() => clearInterval(timer));
}
```

**Errors:** `onCleanup` throws a `TypeError` when `callback` is not a function, and throws
when called after cleanup has started. A failing callback is logged as
`services.cleanup_failed`. For application services, `dispose()` then rejects with an
`AggregateError`. A request cleanup failure never changes the response.

| `onCleanup` | `OnCleanup`   | Registers a callback that releases a resource the factory owns |

## `RequestServicesContext`

```ts
type RequestServicesContext<TCtx = Record<string, unknown>> = {
	readonly ctx: Readonly<Omit<TCtx, "logger">> & { readonly logger: RoutaLogger }
	readonly onCleanup: OnCleanup
```

What a route-file or method services factory receives. It carries no request or handler
input.

| Field       | Type                                          | Purpose                                                                                    |
| ----------- | --------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `ctx`       | `Readonly<Omit<TCtx, "logger">> & { logger }` | Context the middleware before the scope provided, earlier services, and the request logger |
| `onCleanup` | `OnCleanup`                                   | Registers a callback that Routa runs after the response is ready                           |

```ts
import type { RequestServicesContext } from "@routa-ts/core";
```

## `RequestServicesFactory`


Builds one request's route-file or method services. It runs once for each request the scope

| `TServices`    | The scope's service contract                |

```ts
import type { RequestServicesFactory } from "@routa-ts/core";
```

To type a factory for one of your project's scopes, use the generated `ServicesFactory` from

request, releases the scopes the request started, and responds with the standard `500`

## Response Types

```ts
type RouteOutcome = {
	status: number
	description?: string
	schema?: ZodType
	headers?: ZodObject
	cookies?: readonly (AnyCookie | RequiredCookie)[]
}

type RouteResponses = Record<string, RouteOutcome>
type MiddlewareRejectsSpec = RouteResponses

type OutcomeResult<TName extends string, TOutcome> = (TOutcome extends {
	readonly schema: infer TSchema extends ZodType
}
	? { readonly type: TName; readonly data: SchemaOutput<TSchema> }
	: { readonly type: TName; readonly data?: never })
	& OutcomeHeaders<TOutcome>
	& OutcomeCookies<TOutcome>

// Internal helpers, not exported
type OutcomeHeaders<TOutcome> = TOutcome extends { readonly headers: infer THeaders extends ZodType }
	? {} extends SchemaOutput<THeaders>
		? { readonly headers?: SchemaOutput<THeaders> }
		: { readonly headers: SchemaOutput<THeaders> }
	: { readonly headers?: never }

type OutcomeCookies<TOutcome> = TOutcome extends { readonly cookies: readonly (infer TEntry)[] }
	? Extract<TEntry, { readonly required: true }> extends never
		? { readonly cookies?: readonly CookieEffect[] }
		: { readonly cookies: readonly CookieEffect[] } // must include an effect for each required cookie
	: { readonly cookies?: never }

type RoutaResult<TResponses extends RouteResponses> = {
	[K in keyof TResponses]: OutcomeResult<K, TResponses[K]>
}[keyof TResponses]

type RouteRunResult<TResponses extends RouteResponses> = RoutaResult<TResponses>
type InferResponse<TResponses extends RouteResponses> = RouteRunResult<TResponses>

type MiddlewareRejectResult<TRejects extends MiddlewareRejectsSpec> =
	keyof TRejects extends never ? never : RoutaResult<TRejects>

type ResponseChecks<TResponses extends RouteResponses> = {
	readonly [K in keyof TResponses]: OutcomeChecks<TResponses[K]>
}
```

A schema-less outcome forbids `data`, an outcome without headers forbids `headers`, and an
outcome without cookies forbids `cookies`. The source uses named error types for those fields
so the compiler message names the outcome; the block shows them as `never`.

| Type                     | Meaning                                                                      |
| ------------------------ | ---------------------------------------------------------------------------- |
| `RouteOutcome`           | One named outcome in `responses` or `rejects`                                |
| `RouteResponses`         | A route's `responses` map, keyed by outcome name                             |
| `MiddlewareRejectsSpec`  | A middleware's `rejects` map, with the same shape                            |
| `OutcomeResult`          | The result object that selects one outcome                                   |
| `RoutaResult`            | The union of every outcome's result                                          |
| `RouteRunResult`         | What a route's `run` returns                                                 |
| `InferResponse`          | The same union, named for use outside a route                                |
| `MiddlewareRejectResult` | What a middleware `run` returns to reject, or `never` when it declares none  |
| `ResponseChecks`         | Compile-time rules for declared outcomes; a valid outcome adds no constraint |

Use `InferResponse` to type a function that chooses an outcome outside the handler:

```ts
import type { InferResponse, RouteResponses } from "@routa-ts/core";
import { z } from "zod";

export const itemResponses = {
	success: { status: 200, schema: z.object({ id: z.string() }) },
	notFound: { status: 404 },
} as const satisfies RouteResponses;

/** { type: "success"; data: { id: string } } | { type: "notFound" } */
export type ItemResult = InferResponse<typeof itemResponses>;

export function findItem(id: string): ItemResult {
	return id === "1" ? { type: "success", data: { id } } : { type: "notFound" };
}
```
